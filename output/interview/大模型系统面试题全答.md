## 一面

### 3. 解释 FLOPS、TFLOPS、内存带宽、屋顶线模型

`FLOPS` 是每秒浮点运算次数，`TFLOPS` 是 `10^12 FLOPS`。它们描述的是计算吞吐能力。  
`内存带宽` 描述的是单位时间内能搬多少数据，常用 `GB/s` 或 `TB/s`。  
`Roofline` 模型把这两者放到同一张图里，用 `arithmetic intensity = FLOPs / bytes moved` 判断一个 workload 更像是 `compute-bound` 还是 `memory-bound`。

面试时可以这样说：

> 如果一个算子的计算密度低，它会被带宽上限卡住，这时继续追求理论 TFLOPS 没意义；如果计算密度高并且数据复用好，它才更接近算力上限。Roofline 的价值就是帮我们判断优化方向应该优先减少访存，还是继续榨干 FLOPs。

### 4. 分布式训练中 3D 并行（DP/TP/PP）分别解决什么问题？如何组合使用？

`DP` 解决的是吞吐扩展问题：模型能放进单卡，但想通过切 batch 线性放大训练吞吐。  
`TP` 解决的是层内张量太大、单卡放不下或单请求时延太高的问题。  
`PP` 解决的是模型沿深度方向太大、必须跨设备切层存放的问题。

三者组合方式可以理解成：

- `DP`：切样本
- `TP`：切层内矩阵
- `PP`：切层深

常见组合是：

- 小中型模型：`DP + ZeRO/FSDP`
- 超大 dense 模型：`TP + PP + DP`
- 超大 MoE：`EP + TP + DP`，必要时再带 `PP`

一句话：

> 3D 并行不是三种互斥方案，而是分别从 batch、宽度、深度三个轴切模型或数据，组合目标是在显存、通信和吞吐之间找到平衡。

### 5. ZeRO-1/2/3/ZeRO-Offload 的原理和内存节省公式

先定义单卡传统数据并行的主要内存：

- 参数：`P`
- 梯度：`G`
- 优化器状态：`O`

在 Adam + BF16 语境里，常见近似账本是：

- 参数：`2 bytes * N`
- 梯度：`2 bytes * N`
- master weights：`4 bytes * N`
- Adam states：`8 bytes * N`

总计大约 `16 bytes * N` 到 `18 bytes * N` 量级，取决于实现。

如果数据并行度是 `D`：

#### ZeRO-1

只分片 optimizer state。  
单卡显存近似：

`M1 ≈ P + G + O / D`

#### ZeRO-2

分片 optimizer state 和 gradients。  
单卡显存近似：

`M2 ≈ P + G / D + O / D`

#### ZeRO-3

连参数也分片。  
单卡显存近似：

`M3 ≈ P / D + G / D + O / D`

#### ZeRO-Offload

把一部分参数状态或 optimizer state 搬到 CPU，甚至 NVMe。  
本质不是新的 stage，而是在 ZeRO 基础上进一步把显存压力转移到更慢内存层。

一句话总结：

> ZeRO-1/2/3 的本质是逐步把 optimizer、gradient、parameter 从“每卡全量复制”变成“按数据并行组分片持有”；Offload 则是继续把这些状态从 GPU 挪到 CPU 或 NVMe，用带宽换容量。

### 6. PyTorch DDP 和 TorchRun 的启动流程，`--master_port` 为什么容易冲突？

`torchrun` 本质上是一个 launcher。它会：

1. 确定 `nnodes / nproc_per_node / node_rank`
2. 设置分布式环境变量，比如 `RANK`、`WORLD_SIZE`、`LOCAL_RANK`
3. 通过 rendezvous 地址把所有 worker 聚到一起
4. 每个 worker 进入 Python 进程后调用 `init_process_group`
5. 再由 DDP 包装模型，建立梯度同步 hook

`master_port` 容易冲突是因为：

- 它本质是 rendezvous 和进程组初始化要占用的 TCP 端口
- 同一台机器上如果你同时起两组分布式任务，或者上一次任务异常退出没完全释放端口，就会撞
- 多用户共享节点时，如果都用默认端口，也会撞

排查和规避方式：

- 手动指定不同端口
- 启动前 `lsof -i :PORT` 查占用
- 避免写死默认端口
- 异常退出后清理残留进程

### 7. 训练中出现 “CUDA error: all NCCL operations failed” 如何排查？

按五层排查最稳：

#### 1. 进程组和启动层

- `RANK / WORLD_SIZE / LOCAL_RANK` 是否正确
- 所有节点是否真的都启动成功
- 是否有人卡在 dataloader 或 import 阶段导致 collective 超时

#### 2. 网络和拓扑层

- IB / RoCE / 网卡是否正常
- 跨节点能否互通
- `NCCL_SOCKET_IFNAME` 是否绑错
- 是否混用了错误的 NIC 或 hostname

#### 3. GPU 和驱动层

- 驱动 / CUDA / NCCL 版本是否匹配
- 某张卡是否掉卡、Xid、ECC error
- `nvidia-smi topo -m` 是否符合预期

#### 4. 程序逻辑层

- 某个 rank 是否 shape 不一致
- 是否有人提前 OOM 或异常退出
- 是否 collective 调用顺序不一致

#### 5. 观测手段

- 打开 `NCCL_DEBUG=INFO`
- 必要时 `NCCL_DEBUG=TRACE`
- 先缩到单机多卡，再放大到多机
- 先跑最小 all_reduce 脚本排除业务逻辑

一句话：

> NCCL failed 通常不是“通信库自己坏了”，而是启动、网络、驱动、shape、rank 同步顺序这几层里有一层先坏了。

### 8. PagedAttention 的原理是什么？解决了什么痛点？

原理是把 `KV Cache` 从“按请求连续大块分配”改成“按固定 page/block 分配，再通过 block table 间接寻址”。  
这样逻辑上每个请求的 token 仍然是连续的，但物理上不要求 KV 必须连续放在显存里。

它解决的核心痛点：

- 长上下文和动态请求流下，KV cache 连续分配容易碎片化
- 请求长度不可预知，按 `max_seq_len` 预留太浪费
- Continuous batching 场景中，请求不断加入/退出，显存布局非常动态

一句话：

> PagedAttention 不是让 attention 数学更快，而是让 KV cache 的显存管理更像虚拟内存系统，从而提高显存利用率并支撑动态调度。

### 9. 连续批处理 vs 传统批处理，吞吐提升多少？

没有统一固定数字，但真实在线 workload 下常见是：

- 保守：`1.2x ~ 1.5x`
- 常见：`1.5x ~ 3x`
- 极度 ragged 的 decode 场景会更高

原因是传统 batching 必须等整批对齐，容易被最长请求拖住；`continuous batching` 则允许 iteration 级动态进出，请求完成后空位能被立刻填上。

面试里建议这样答：

> 连续批处理的提升没有固定值，它高度依赖输出长度分布和调度实现。真实收益通常不是来自单次 kernel 更快，而是来自减少等待和提高 decode 阶段 GPU 持续装载率。

### 10. FP8、INT8、AWQ、GPTQ、SmoothQuant 的区别和适用场景

#### FP8

- 低精度浮点
- 适合训练和高性能推理
- 对硬件要求高，H100/Blackwell 这类新硬件更友好

#### INT8

- 通用 8-bit 整数量化
- 工程成熟度高
- 训练后量化和量化感知训练都常见

#### AWQ

- 面向 LLM 的权重量化方法
- 核心是保护对激活敏感的权重通道
- 适合离线压缩后部署推理

#### GPTQ

- 面向 LLM 的后训练权重量化
- 用 Hessian 近似做逐层误差补偿
- 优点是精度通常不错，适合离线单模型压缩部署

#### SmoothQuant

- 把 activation outlier 迁移到权重侧，让 activation 更容易做 INT8
- 适合做 W8A8 这类更均衡的量化部署

一句话比较：

- 想保训练和高吞吐，先看 `FP8`
- 想工业级通用推理，先看 `INT8 / SmoothQuant`
- 想做 LLM 离线权重量化部署，`AWQ / GPTQ` 更常见

### 11. 手推 Transformer 单次前向的显存占用公式（参数 + KV Cache + 激活）

设：

- 层数 `L`
- hidden size `H`
- batch `B`
- 序列长度 `S`
- 参数总量 `N`
- 元素字节数 `b`

#### 参数

`M_param ≈ N * b`

#### KV Cache

对 decoder-only Transformer，单 token 每层要存 K 和 V。  
若 KV head 数为 `H_kv`，head dim 为 `D`：

`M_kv ≈ B * S * L * 2 * H_kv * D * b`

如果用 `GQA/MQA`，这里的 `H_kv` 会比 query head 数小。

#### 激活

最粗略近似：

`M_act ≈ c * B * S * H * L * b`

其中 `c` 是跟实现相关的常数，取决于是否保存 attention 中间结果、是否 checkpoint、是否 fused kernel。

所以单次前向总显存可以写成：

`M_total ≈ M_param + M_kv + M_act`

训练时还要再加：

- gradients
- optimizer states

### 12. 手写算法：实现一个简单的 KV Cache 管理类，支持分页和 LRU 淘汰

```python
from collections import OrderedDict


class Page:
    def __init__(self, page_id, capacity):
        self.page_id = page_id
        self.capacity = capacity
        self.tokens = []

    def full(self):
        return len(self.tokens) >= self.capacity


class KVCacheManager:
    def __init__(self, num_pages: int, page_size: int):
        self.page_size = page_size
        self.free_pages = [Page(i, page_size) for i in range(num_pages)]
        self.req_to_pages = {}
        self.lru = OrderedDict()  # req_id -> None

    def _touch(self, req_id):
        if req_id in self.lru:
            self.lru.move_to_end(req_id)
        else:
            self.lru[req_id] = None

    def _alloc_page(self):
        if self.free_pages:
            return self.free_pages.pop()
        victim_req, _ = self.lru.popitem(last=False)
        self.evict(victim_req)
        return self.free_pages.pop()

    def append_token(self, req_id, token_kv):
        pages = self.req_to_pages.setdefault(req_id, [])
        if not pages or pages[-1].full():
            pages.append(self._alloc_page())
        pages[-1].tokens.append(token_kv)
        self._touch(req_id)

    def get_pages(self, req_id):
        self._touch(req_id)
        return self.req_to_pages.get(req_id, [])

    def evict(self, req_id):
        pages = self.req_to_pages.pop(req_id, [])
        for p in pages:
            p.tokens.clear()
            self.free_pages.append(p)
        self.lru.pop(req_id, None)
```

这个版本抓住了三点：

- 分页分配
- 请求到 page 的映射
- LRU 淘汰

### 4. 如何把 130B 模型的推理延迟从 2s 降到 80ms？请给出具体技术方案

严格说单靠一个优化很难从 `2s -> 80ms`，必须分阶段。

#### 第一层：定义目标

- 是 `TTFT` 还是 `ITL` 还是端到端 P99
- 是单请求低时延还是高并发低时延

#### 第二层：模型和系统组合拳

- 更激进量化：`FP8 / INT8 / AWQ/GPTQ`
- `TP` 压低单请求时延，必要时 `PP`
- 高性能 attention kernel：`FlashAttention / FlashDecoding`
- `PagedAttention + Continuous Batching`
- `Prefix Caching`
- `Speculative Decoding`
- 必要时 `PD 分离`

#### 第三层：工程细节

- CUDA Graphs
- fused kernels
- 请求预处理和 tokenizer pipeline
- CPU/GPU overlap
- 网卡和拓扑调优

面试里可以这么收束：

> 从 2s 到 80ms 这种量级，通常不是单点优化，而是量化、并行、kernel、调度和缓存复用一起上；如果是严格低时延目标，我会优先明确 TTFT 还是 ITL，再决定是走 TP + kernel + speculative 这条线，还是进一步做 P/D 分离。

### 5. vLLM、TGI、TensorRT-LLM、ImDeploy、SGLang 在推理加速上的核心区别

#### vLLM

- 强项：`PagedAttention + Continuous Batching`
- 定位：通用高吞吐开源 serving

#### TGI

- 强项：工程集成、Hugging Face 生态、部署友好
- 定位：更偏产品化服务网关

#### TensorRT-LLM

- 强项：NVIDIA 体系深度优化，kernel 和 engine 极强
- 定位：追求极致吞吐/时延的生产部署

#### SGLang

- 强项：前缀组织、程序化推理、长前缀复用
- 定位：更偏“推理语言 + 系统”的组合

#### MMDeploy/ImDeploy

- 强项：更偏多模态/部署工具链和模型落地
- 定位：模型部署平台，不完全等价于 vLLM 这种 LLM serving engine

一句话：

> vLLM 偏通用高吞吐，TensorRT-LLM 偏极致性能，TGI 偏部署生态，SGLang 偏前缀复用和程序化推理，MMDeploy 更偏部署工具链。

### 6. FlashAttention-2 / FlashDecoding 的加速原理？为什么比原生注意力快 3-10 倍

#### FlashAttention-2

- 不是减少 FLOPs，而是减少 HBM 读写
- 用 tiling + online softmax + 本地状态累积，避免显式 materialize 大矩阵
- `FA2` 的 work partition 更合理，输出归属更清晰，减少中间状态回写

#### FlashDecoding

- 面向 decode 场景优化
- decode 时 query 长度通常是 1，但 KV 很长，所以瓶颈更偏 memory-bound
- 核心是更高效地并行遍历和归并长 KV cache，减少串行瓶颈和低效访存

为什么会快 3-10 倍：

- 原生实现频繁物化中间张量
- HBM 往返多
- 对长序列和 decode 场景不友好

一句话：

> 它们快的核心不是数学变少，而是数据流更接近 GPU 友好路径，把 attention 从“中间矩阵驱动”改成“本地状态驱动”。

### 7. Speculative Decoding 原理？Medusa、Lookahead Decoding、EAGLE 区别

`Speculative Decoding` 的通用原理是：

1. 先生成一串候选 token
2. 再用更强模型并行验证
3. 接受一部分，拒绝时回退

#### Medusa

- 不是单独的小 draft model
- 而是在同一主模型上加多个预测头，一次提出多个未来 token 候选

#### Lookahead Decoding

- 更像利用搜索式或前瞻式候选展开
- 强调多步候选的提前探索和批量验证

#### EAGLE

- 通过更轻量的 auxiliary predictor 预测未来 hidden/token
- 目标是提高接受率，减少重算

一句话比较：

- `经典 speculative`：小模型猜，大模型验
- `Medusa`：主模型自己多头猜
- `Lookahead`：更偏前瞻式候选展开
- `EAGLE`：更偏 hidden-level 预测和高接受率设计

### 8. MoE 模型训练为什么更容易 OOM？如何优化

更容易 OOM 的原因：

- expert 参数总量大
- `all-to-all` 需要额外 dispatch buffer
- 某些 expert 热点严重，局部 batch 暴涨
- 激活和路由中间状态额外增加

优化手段：

- 减少 `capacity factor`
- 强化 load balance loss
- expert parallel + tensor parallel 合理组合
- activation checkpoint
- 更小的 router / top-k 调整
- 混合精度和量化
- 优化 all-to-all overlap

### 9. 1000 张 H100 集群常见的网络拓扑是什么？单节点 8 卡 vs 跨节点 8 卡哪个性能更高

常见拓扑：

- 单节点内：`NVLink / NVSwitch`
- 跨节点：`InfiniBand` 或高性能以太网 `RoCE`
- 大规模常见胖树、Dragonfly+、Clos/Fat-Tree 风格的分层交换网络

单节点 8 卡通常明显强于跨节点 8 卡，因为：

- 节点内 NVLink/NVSwitch 带宽更高、时延更低
- 跨节点即便是 400G/800G IB，仍然更贵

一句话：

> 如果通信模式频繁且细粒度，比如 TP，单节点 8 卡通常远好于跨节点 8 卡；跨节点更适合 PP、DP 这类通信形态相对粗粒度的并行。

### 10. GPU 利用率只有 30%，可能的原因有哪些？给出排查清单

排查清单：

#### 数据层

- dataloader 太慢
- CPU 预处理瓶颈
- 存储 IO 不足

#### kernel 层

- 小 batch 导致 occupancy 低

#### 通信层

- all_reduce / all-to-all 等待
- 跨节点链路瓶颈
- 通信和计算没有 overlap

#### 内存层

- attention/KV cache memory-bound
- 显存碎片
- host-device copy 太多

#### 调度层

- 请求流量太稀
- continuous batching 不充分
- prefill/decode 干扰

观测手段：

- Nsight Systems
- Nsight Compute
- NCCL trace
- GPU util / SM util / memory BW / link util

### 11. 如何在 2×24G 显卡上跑通 70B 模型？需要用到哪些技术组合

如果要求“能跑通”，而不是“高吞吐生产可用”，通常需要组合拳：

- `4-bit / 8-bit` 权重量化，优先 `AWQ / GPTQ / bitsandbytes`
- CPU offload
- 分层或分片加载
- `TP=2` 或者更轻量的 model sharding
- 低 batch、短 context
- KV cache 限制

一句话：

> 2×24G 跑 70B 基本不可能靠全精度硬上，必须依赖强量化 + CPU offload + 极小 batch/context，这更像“功能跑通”而不是高性能部署方案。

### 12. 手写算法：实现一个简单的 Ring AllReduce 通信原语

```python
def ring_allreduce(chunks, rank, world_size, send, recv):
    """
    chunks: list of local tensor shards, len == world_size
    send(dst, tensor), recv(src) are abstract transport APIs
    """
    # reduce-scatter
    for step in range(world_size - 1):
        send_to = (rank + 1) % world_size
        recv_from = (rank - 1 + world_size) % world_size

        send_idx = (rank - step) % world_size
        recv_idx = (rank - step - 1) % world_size

        send(send_to, chunks[send_idx])
        incoming = recv(recv_from)
        chunks[recv_idx] += incoming

    # all-gather
    for step in range(world_size - 1):
        send_to = (rank + 1) % world_size
        recv_from = (rank - 1 + world_size) % world_size

        send_idx = (rank - step + 1) % world_size
        recv_idx = (rank - step) % world_size

        send(send_to, chunks[send_idx])
        chunks[recv_idx] = recv(recv_from)

    return chunks
```

这段代码抓住了 ring all-reduce 的本质：

- 先 `reduce-scatter`
- 再 `all-gather`

### 7. 3D 并行下，TP=8、PP=4、DP=2 时，global batch size 与 micro batch 的关系

若：

- `DP = 2`
- `PP = 4`
- 梯度累积步数 `GA`
- 每个 pipeline step 的 micro-batch size 为 `m`

则：

`global_batch_size = DP * m * GA`

如果每次一个 pipeline flush 中有 `num_micro_batches = K`，那通常：

`GA = K`

所以常写成：

`global_batch_size = DP * micro_batch_size * num_micro_batches`

注意：

- `TP` 不影响 batch 维度，只影响模型切分
- `PP` 本身也不直接乘到 global batch 上，它通过 micro-batch 数决定流水线填充

### 13. 手写算法：实现一个简单的动态批处理调度器

```python
from collections import deque


class Request:
    def __init__(self, req_id, prompt_len, max_new_tokens):
        self.req_id = req_id
        self.prompt_len = prompt_len
        self.max_new_tokens = max_new_tokens
        self.generated = 0
        self.done = False


class DynamicBatchScheduler:
    def __init__(self, max_batch_size, max_tokens_per_step):
        self.waiting = deque()
        self.running = []
        self.max_batch_size = max_batch_size
        self.max_tokens_per_step = max_tokens_per_step

    def submit(self, req: Request):
        self.waiting.append(req)

    def _admit(self):
        token_budget = self.max_tokens_per_step - len(self.running)
        while self.waiting and len(self.running) < self.max_batch_size and token_budget > 0:
            req = self.waiting.popleft()
            self.running.append(req)
            token_budget -= 1

    def step(self):
        self._admit()

        finished = []
        for req in self.running:
            req.generated += 1
            if req.generated >= req.max_new_tokens:
                req.done = True
                finished.append(req)

        self.running = [r for r in self.running if not r.done]
        return finished
```

这段代码体现的是：

- 有 waiting queue
- 每个 decode step 动态准入
- 已完成请求退出
- 下一轮继续补位

这就是 continuous/dynamic batching 的最小骨架。
