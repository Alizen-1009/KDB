# Agent 场景 KV Cache 空间不足时如何优化？

- 整理状态：已整理
- 题目出处：用户提供的《英伟达 AI Infra 五面面经》截图，AI Infra 与推理系统第 5 题；2026-11-05 收录，实际面试日期与具体轮次未提供。

## 原题与条件

针对 Agent 场景，KVCache 空间不够，有没有什么优化？

## 30 秒回答

区分活跃生成 KV 与等待工具的会话缓存。先通过前缀/分支共享、分页和缓存感知路由减少重复与浪费；等待中的会话可卸载并在恢复前预取。进一步可用 KV 量化、上下文并行，或在接受语义变化时做摘要裁剪；不能把分页或卸载说成减少了逻辑上下文。

## 深入解释

| 路线 | 作用 | 边界 |
|---|---|---|
| 公共前缀、分支共享 | 多个分支复用同一份物理 KV | 修改共享尾块需正确引用计数/写时复制 |
| 分页管理 | 减少预分配浪费与外部碎片 | 不缩小真实已存 KV 数据 |
| GPU/CPU/存储分层 | 将等待会话移出 GPU，恢复前预取 | 增加搬运、预取和排队成本 |
| 缓存感知路由 | 下一轮尽量回到已有会话缓存的位置 | 还要兼顾负载，不能只追求命中 |
| KV 量化 | 减少每 token 字节数 | 验证精度、scale 开销、反量化效率 |
| 上下文并行 | 把单请求历史 KV 分到多卡 | 引入 Q、partial output/LSE 通信 |
| 摘要、裁剪 | 减少模型实际处理的历史 | 会改变模型可见信息，通常不是无损优化 |

Agent 等待工具时通常暂不需要执行模型 forward，给卸载和异步预取提供机会；需要处理工具返回时间不确定和恢复抖动。淘汰无引用缓存、卸载会话状态、丢弃仍需使用的活跃 KV 是不同动作，不能混为一谈。
