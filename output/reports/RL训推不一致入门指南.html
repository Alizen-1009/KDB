RL 训推不一致入门指南

为什么同一个模型会给同一批 token 算出不同概率，以及如何修复

适用范围：这是给刚接触 PPO / GRPO 的工程师准备的工程机制指南。它提供诊断顺序与方法边界，不提供脱离模型、dtype、后端、序列长度和算法的无条件统一阈值。
阅读任务：建立正确心智模型预计：15–20 分钟wiki 归纳 + 一手资料

01 / LOOP先记住一句话

训推一致性不是要求两个程序“长得一样”，而是要求同一策略快照在同一条件上下文上，对同一 token 给出同一条件概率语义。
Rollout engine用行为策略生成真实 token IDs，并记录 old logprob 与采样元数据。
Reward对 response 打分或验证，不应悄悄改变被训练的 token 轨迹。
Trainerteacher forcing 重算 logprob，构造 PPO / GRPO loss 并更新参数。
Weight Sync把新策略权重传回 Rollout；传输完成不等于原子版本切换完成。

02 / DEFINITION什么叫“不一致”

一致性测试的三个固定条件：同一 policy snapshot、同一 token IDs、同一条件上下文（历史 token、mask、position、logprob 语义一致）。

对每个 response token 比较：log πθ(yt | x, y<t)

如果 Rollout 与 Trainer 对这同一个条件概率给出系统性不同的 per-token logprob，就是训练—推理执行路径的不一致。

预期差异：optimizer update 之后，new policy 与冻结的 old policy 不同，本来就是 PPO / GRPO 要测量的策略变化。
错误基线：拿更新后的 Trainer 与更新前 Rollout 直接比较，再把差异都叫 mismatch。正确基线必须在无 optimizer update或冻结 snapshot下测；异步系统还必须记录 policy version / staleness。

03 / ALIGNMENT为什么逐 token decode 与一次 full forward 理论等价

Decoder-only causal LM 无论是 Rollout 的 prefill + decode，还是 Trainer 的 teacher forcing full forward，计算的都是同一个自回归分解。执行调度不同，不等于概率定义不同。

不要混淆两张 mask：prompt loss mask 可以让 prompt 不进入 RL loss；attention mask 仍必须让 response 看见完整 prompt。prompt loss mask ≠ attention mask。

04 / IMPACT为什么会伤害 PPO / GRPO

常见 ratio 形式可写为：

ratio = exp(train_logp − rollout_logp)

当 snapshot 冻结且还没发生 optimizer update 时，本来希望 delta≈0、ratio≈1。执行路径 mismatch 会把系统差异伪装成策略变化，进而扭曲 clipping、advantage 加权与相关监控。指数映射还会让 logprob 差异呈非线性放大。

Ratio 本地计算器 教学示例

delta0.2000
ratio1.2214

该 token 在 Trainer 路径下的概率约为 Rollout 的 1.22 倍。这里只是数学映射，不代表安全或危险阈值。

边界：默认值 −2.2 与 −2.0 是教学假设，不是 benchmark，也不是任何框架的健康线。

默认教学示例：rollout = −2.2，trainer = −2.0，因此 delta = 0.2，ratio = exp(0.2) ≈ 1.2214。该数值不是 benchmark 或通用阈值。

06 / ROOT CAUSES六类根因：症状 → 最小检查 → 典型修复

顺序有意从语义层走向数值层。先证明两边在算同一个东西，再讨论浮点与 kernel。

ROOT 01Token / chat template / BOS–EOS / stop

症状
首尾 token、assistant header 或截断附近集中偏差；长度偶尔差一。
最小检查
逐个比较 Rollout 保存的 prompt_token_ids、response_token_ids、stop token 归属；禁止 detokenize 后再 tokenize。
典型修复
直接复用真实 IDs；固定 chat template、BOS/EOS 与 generation prompt 规则；明确 stop token 是否进入 response。

ROOT 02Causal shift 与 attention / loss mask

症状
所有 response token 整体错一位；首 token 最明显；padding 或 packing 边界异常。
最小检查
手算一条短样本，确认 logits[prompt_len−1]→response[0]；分别打印 response loss mask 与 attention mask。
典型修复
用 logits[:, :-1] 对 ids[:, 1:]；让 response 可见完整 prompt；隔离 packed sequence 边界。

ROOT 03Raw vs processed logits / temperature / top-p / top-k

症状
高概率 token 看似接近，受 suppression、penalty 或截断影响的 token 明显偏离。
最小检查
关闭 temperature、top-k/top-p、repetition penalty、token suppression；明确保存的是 raw model logprob 还是行为采样分布 logprob。
典型修复
统一 logprob 语义；若要校正行为策略，就完整保存 processor 配置与处理后的概率定义。

ROOT 04Position / RoPE / padding / packing / KV cache

症状
误差随位置增长；left/right padding、长上下文或 cache page 边界处跳变。
最小检查
对比 position IDs、RoPE scaling、padding side、sequence boundaries、cache dtype 与写入范围；先禁用 prefix/paged cache。
典型修复
对齐 position/config；显式携带每条序列位置元数据；修复 packing isolation 与 KV cache 边界。

ROOT 05Policy version / LoRA / 量化 / 权重同步 / staleness

症状
同批样本按 worker 或 policy version 分群；同步后仍偏；adapter/量化开关改变结果。
最小检查
记录 policy version、权重 hash/epoch、LoRA merge 状态、量化配置；在 barrier 后做 frozen zero-update。
典型修复
原子版本切换；轨迹绑定生成版本；同步 base、adapter 与量化参数。跨 Mesh reshard 只负责数据路径，不替代版本语义。

ROOT 06Dtype / kernel / TP reduction / dynamic batch

症状
同一语义下仍有尾部异常；误差随 batch、TP degree、Flash/Paged backend 或低精度改变。
最小检查
单卡、高精度、eager、固定 batch，无量化/Flash/Paged；再一次只恢复一个变量。
典型修复
统一 precision/backend；采用 deterministic 或 batch-invariant 路径做基线；必要时调整规约与 softmax/log-softmax 精度。

07 / FUNNEL排查漏斗：先修语义，再谈补偿

每一步都应保留一个可复现的小样本。若失败，先在当前层修复；通过后才恢复下一层复杂度。

保存 Rollout 原始 artifacts真实 prompt/response token IDs、per-token logprob、policy version、sampling/position/mask 元数据。
缺字段？ 先补观测性，不要靠文本重建轨迹。
Frozen zero-update test冻结同一 snapshot，权重同步后不做 optimizer update，重算同一批 token。
通过？ 差异更可能来自预期 policy update / staleness；失败？ 继续向下。
单卡 + 高精度 + eager + 无 processor关闭 temperature/top-k/top-p/penalty、量化、Flash/Paged cache、并行和动态 batching。
仍失败？ 高概率是 token / shift / mask / position / 权重语义错误。
Token → causal shift → mask字节级核对 IDs；验证首个 response token 来自最后 prompt 位置；分开 attention 与 loss mask。
原则：任何语义错误都必须在这里消掉，TIS 不能替你修错 token。
Position → policy version核对 position/RoPE/padding/packing 元数据，再核对 LoRA、量化权重与原子版本切换。
按组看：按 worker、batch、backend、policy version 切片，寻找系统分群。
逐项恢复性能路径一次恢复一项：Flash → Paged/KV quant → TP/EP → quant → dynamic/continuous batching。
每恢复一项：重跑同一 frozen corpus，比较 delta 尾部与随位置走势。
决策规则：先消除错 token、错 shift、错 mask、错位置与错权重版本；只有在语义基线正确、执行差异不可完全消除或 off-policy 本来就是设计的一部分时，才评估 TIS / rejection / masking。

08 / METHODS解决方法分层矩阵

A根因消除
优先级最高。复用 exact token IDs；正确 causal shift / mask；统一 raw 或 processed logprob 语义；使用原子 weight version；对齐 position、RoPE、padding、packing 与 config。
首选
能修就不要补偿。这里解决的是“算错东西”。
B数值执行对齐
在诊断基线中使用同 precision / backend；选择 deterministic 或 batch-invariant 路径；从单卡高精度/eager 基线逐项恢复低精度、kernel、TP/EP 与 batching。
wiki 归纳
严格路径可能牺牲吞吐，适合作为校准基线，不一定适合永久生产。
C算法缓解
TIS / IS reweight、rejection、masking： ρ = πtrain / πrollout 对 correction ratio 截断可抑制极端权重与方差；拒绝或 masking 可移除高 mismatch token / sequence。
版本相关
截断会引入偏差或改变有效优化问题；只能缓解 off-policy 影响，不能修复错 token / 错 mask。VeRL 的具体模式、聚合层级与配置以对应版本官方文档为准。
DMoE 专项
Router Replay / R3：在 Rollout 保存每个 token 的 expert assignments（或路由选择），训练 forward 时 replay，使两条路径选择同一组专家；训练侧仍可基于训练 logits 计算门控权重并保留梯度路径。
一手资料 版本相关
不适用于 dense；增加 payload、packing/CP 对齐与回放复杂度。NeMo RL 当前支持的 policy/trainer/rollout 组合以官方 Router Replay 文档为准。
什么时候用 TIS / R3？
观察先做什么可考虑不要误用
dense 或 MoE；语义已对齐，但 rollout/train 执行栈仍有 off-policy gap 或异步 staleness用 frozen 基线量化 delta/ratio 与尾部；校准阈值和粒度TIS / IS、rejection 或 masking不要拿它掩盖 retokenize、off-by-one、mask、版本 bug
MoE；路由选择在 rollout 与 training 之间不一致，并显著贡献 mismatch先证明 token/position/权重一致，并保存 route identityR3 / Router Replay；可与其它策略独立评估dense 没有 expert routing；R3 也不会修 token/mask/kernel 的所有问题

09 / MINIMUM TEST最小一致性测试

伪代码 下方不绑定任何框架 API。真实 tensor shape、padding、mask、device 与 gather API 必须按你的框架适配。

ids = cat(prompt_ids, response_ids)
logp_next = log_softmax(model(ids).logits[:, :-1], dim=-1)
targets = ids[:, 1:]
token_logp = gather(logp_next, targets)
response_logp = token_logp[:, prompt_len - 1 : prompt_len - 1 + response_len]
# PSEUDOCODE — freeze one policy snapshot; no optimizer update
artifact = load_rollout_artifact(sample_id)
assert exact_equal(artifact.prompt_token_ids, prompt_ids)
assert exact_equal(artifact.response_token_ids, response_ids)
assert artifact.policy_version == loaded_policy_version

trainer_logp = recompute_with_correct_shift(artifact)
delta = trainer_logp - artifact.rollout_logprobs
ratio = exp(delta)

report_distribution(delta, ratio)
report_by_token_position(delta)
report_by_group(delta, keys=[
    "backend", "batch_shape", "policy_version"
])
# Do not reduce the diagnosis to one average or one universal threshold.

每条轨迹至少保存

  • prompt_token_ids
  • response_token_ids
  • prompt_len
  • rollout_logprobs（注明 raw / processed）
  • policy_version
  • sampling_config
  • position / mask metadata
  • 建议追加：backend、dtype、batch shape、LoRA/quant 配置、stop reason
验收语义：这个测试不是要求所有生产路径 bitwise identical，而是先建立一条可解释的 frozen baseline，再用分布、尾部和分组证据判断真实路径的偏差是否系统性地影响 ratio。

10 / METRICS监控什么：不只看平均值

Delta 与方向

  • delta mean：是否有整体正/负方向
  • MAE：平均绝对差
  • p95 / p99 / max：尾部和极端 token
  • 按 token 位置画趋势：是否累积或在边界跳变
示意：无明显方向、尾部受控。不是阈值图。

Ratio 与分组

  • exp(delta) 的中心、尾部与非对称性
  • 按 backend、batch shape、worker 分组
  • 按 policy version / staleness 分组
  • 按序列长度、token 位置、TP/EP 配置分组
示意：随位置扩大，需要优先查 position/cache/累积数值路径。
禁止单指标结论：不要只看一个平均相对误差。logprob 接近 0 时，相对误差的分母会让指标不稳定；平均值还会掩盖正负抵消和重尾。不存在脱离模型、dtype、序列长度、后端、token 分布与 RL objective 的通用健康阈值。

11 / MYTHS初学者常见误区

“训练只输入 response 就够了。”

错误。response 的条件概率依赖完整 prompt 与已生成 prefix；除非框架显式复用了正确 cache/上下文。

“Prefill/decode 和 full forward 本来就不是同一概率。”

错误。只要历史 token、权重、mask、position 与 logits 语义一致，它们实现同一自回归条件概率。

“Prompt 不进 loss，所以也不进 attention。”

错误。loss mask 与 attention mask 不同；response 必须看见 prompt。

“固定 seed 就能解决一致性。”

错误。seed 主要约束采样随机性；batch-dependent kernel、规约顺序、token/position/权重错误仍在。

“平均误差很小，就一定安全。”

错误。尾部 token、方向偏差与 advantage / clipping 的交互可能更关键。

“TIS 能修所有 bug。”

错误。TIS 只能重加权或限制 off-policy 影响，不能把错 token、错 shift、错 mask 变对。

“MoE 的 R3 也适用于 dense。”

错误。R3 回放的是 expert assignment；dense 模型没有对应路由机制。

“Actor–reference KL 就是训推一致性指标。”

错误。它比较两种 policy；一致性基线比较同一预期 policy 的两条执行路径。

“把 rollout 文本重新 tokenize 也可以。”

错误。文本往返可能改变空格、特殊 token、模板边界或不可逆规范化；应保存并复用原始 IDs。

13 / EVIDENCE来源与证据边界

已知事实 一手资料 / 基础机制

自回归 causal shift、同 snapshot 的 token 级条件概率定义、ratio 的指数关系，以及 Router Replay 保存并回放 MoE 路由选择，均可由代码级推导、官方文档或论文方法描述核验。

实现差异 版本相关

VeRL rollout correction 的模式、聚合层级、配置名；NeMo RL Router Replay 支持的 rollout/trainer 组合与 payload 路径都可能随版本变化，必须以所用版本官方文档和源码为准。

性能权衡 wiki 归纳

高精度、deterministic / batch-invariant kernel 与简化并行有助于建立诊断基线，但可能牺牲吞吐、并发与部署效率；应逐项恢复而非永久全关。

待核实 / 不提升为通用事实 边界

固定 KL、β、误差或 ratio 阈值；某个 dtype / kernel 的统一安全线；未经绑定版本的框架 API；单篇实验中的性能数字，都不作为本指南的普适结论。
