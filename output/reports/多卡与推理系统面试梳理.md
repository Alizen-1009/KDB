# 多卡与推理系统面试梳理

## 说明

这份文档基于现有 wiki 中的 `[[Tensor Parallelism]]`、`[[集合通信]]`、`[[Continuous Batching]]`、`[[KV Cache]]`、`[[PD分离]]`、`[[Prefix Caching]]` 等条目整理，目标是给出一版偏面试口径的系统讲解。  
其中 `EP`、`PD 解耦 vs PD 分离`、以及“命中 Prefix Caching 后 attention 传参与执行路径有什么变化”属于在现有资料上的工程归纳，适合作为答题框架，但仍值得后续补独立来源。

## 1. 如果被问“有没有做过多卡 / 分布式通信”，应该怎么介绍

一个比较稳的回答方式不是先堆术语，而是先说你理解的对象分层：

- 最底层是 `NCCL` 这类通信 backend，真正把多卡 collective 落到 NVLink / NVSwitch / PCIe / IB 上
- 中间层是 `torch.distributed`，暴露 `all_reduce`、`all_gather`、`reduce_scatter`、`send/recv` 等接口
- 上层才是具体并行策略，比如 `DP / TP / PP / EP / ZeRO / FSDP`

如果要一句话概括，可以说：

> 我理解多卡系统的关键不只是“会用哪个并行策略”，而是知道不同策略本质上在什么时刻、对什么张量调用什么通信原语，以及这些通信为什么会成为瓶颈。

## 2. TP 是什么，TP 里常见通信原语是什么

`TP` 的核心是：**在单层内部按张量维度切开权重和计算，让多张 GPU 一起完成同一层。**

它常用于：

- 单卡放不下模型
- 希望压缩单请求时延
- 节点内互联足够快，能承受高频同步

### TP 常见通信原语

最常见的是这几个：

- `all_gather`
- `reduce_scatter`
- `all_reduce`

可以这么理解：

### 1. 列并行（column parallel）后常需要 gather

比如一个线性层权重按输出维切开，每张卡算出一部分输出。如果下一步需要完整激活，就要：

- `all_gather`：把各卡局部输出拼成完整张量

### 2. 行并行（row parallel）后常需要 reduce

如果权重按输入维切开，每张卡只拿输入的一部分，最后得到的是对同一输出的局部贡献，就要：

- `all_reduce`：把所有卡的局部结果求和
- 或 `reduce_scatter`：如果后续还能继续分片消费，就不一定要先 gather 成完整结果

### 3. 一个好记忆方式

- `all_gather`：我缺别人的分片，要把完整张量凑出来
- `all_reduce`：我手上是对同一个结果的局部贡献，要加总
- `reduce_scatter`：先做 reduce，再把结果按分片发回去，省一次中间完整张量落地

### TP 的面试重点

面试里通常不只问“TP 是什么”，而是会继续追：

- 为什么 TP 更适合节点内，不太适合跨节点大规模拉长？
- 为什么 TP 每层都通信，所以带宽压力很重？
- 为什么 TP 往往和 `Sequence Parallelism` 一起用来缓解激活显存？

一句话答法：

> TP 的优势是时延低、单层拆分细，但代价是每层都要同步，所以它本质是拿通信换单卡容量和单请求时延。

## 3. MoE / EP 要怎么讲

### 1. MoE 的系统本质

`MoE` 的关键不只是稀疏激活，而是把：

- `total params`
- `active params`

这两件事拆开。每个 token 只激活少数 expert，所以总参数可以很大，但每 token 的 FLOPs 不会同比例膨胀。

### 2. EP 是什么

`EP` 可以理解为 `Expert Parallelism`：

- 不同 expert 分布在不同 GPU / 不同节点上
- router 先决定每个 token 去哪些 expert
- 系统再把 token dispatch 给目标 expert，算完再 gather 回来

### 3. EP 的核心通信

EP 最典型的通信不是 `all_reduce`，而是：

- token dispatch
- token gather
- 本质上经常接近 `all-to-all`

这也是 MoE 系统最容易被问到的点：  
**MoE 的理论 FLOPs 很省，但如果 dispatch / gather 做不好，通信和负载不均会把收益吃掉。**

### 4. 面试里可以强调的难点

- router 导致 expert 热点不均衡
- token 数量是动态的，很难静态分配
- 不同 expert 上 batch size 很碎，kernel 利用率可能变差
- 跨卡 `all-to-all` 很容易成为瓶颈

一句话答法：

> EP 本质是在 FFN 维度做“稀疏路由 + token 搬运”，所以它的系统难点不只是算 expert，而是 dispatch、负载均衡和碎片化 batch 管理。

## 4. Continuous Batching 和 KV Cache 分配要怎么一起讲

### 1. Continuous Batching

`Continuous Batching` 的核心是：

**不是等整批请求全部结束再换批，而是在每个 decode iteration 之后动态让新请求加入、旧请求退出。**

这样可以：

- 提高 decode 阶段吞吐
- 降低真实流量下的空转
- 更好适配不同输出长度的 ragged requests

### 2. 为什么它和 KV Cache 强相关

因为 decode 阶段每个请求都带着自己的 KV Cache 状态。  
调度器每次重组 batch，本质上不仅是在拼 token，还在管理：

- 哪些请求还活着
- 每个请求的 cache page / block 在哪
- 哪些请求需要扩容 KV
- 哪些请求结束后可以回收 KV

### 3. KV Cache 分配的工程重点

可以从三层说：

- 容量：每个请求会随着生成不断增长，需要动态扩容
- 布局：如果必须连续分配，容易碎片化；所以像 `[[PagedAttention]]` 这种分页思路很关键
- 生命周期：请求结束时及时回收；共享前缀时要考虑引用计数、copy-on-write 或 page 共享

一句话答法：

> Continuous batching 的难点不是“能不能把请求塞进 batch”，而是要在 iteration 级调度下，持续维护 ragged batch 对应的 KV Cache 分配、映射和回收。

## 5. 单卡场景下，P 和 D 怎么衔接

这里的 `P` 是 `Prefill`，`D` 是 `Decode`。

在单卡场景下，通常不是两套硬件，而是同一张卡上两个阶段顺序衔接：

1. `Prefill` 先把整段 prompt 跑完
2. 把每层历史 token 的 `K/V` 写入 KV Cache
3. 产出第一个 token
4. 之后进入 `Decode` 循环，每步只算新 token 的 `Q/K/V`
5. 用新 token 的 `Q` 去和历史 KV Cache 做 attention，再生成下一个 token

所以单卡里 `P -> D` 的关键接口其实就是：

- `prefill` 产出的每层 KV Cache
- decode 所需的 position / sequence length / page table / cache handle

如果说得更工程一点：

> 单卡里 P 和 D 的衔接，本质就是“prefill 把上下文压进 KV Cache，decode 接管这个状态继续做增量生成”。

## 6. PD 解耦和 PD 分离有什么区别

这是一个很容易被混着说的点。

### 1. PD 解耦

`PD 解耦` 更偏逻辑层或软件层：

- prefill 和 decode 在调度、队列、运行时上被区分开
- 但不一定部署在不同物理资源上
- 同一张卡、同一节点里也可以做“逻辑解耦”

它强调的是：

- 两个阶段的调度目标不同
- 资源竞争要尽量减少
- 内部 runtime 不要把它们当成一种任务处理

### 2. PD 分离

`PD 分离` 更偏部署层或资源层：

- prefill cluster 和 decode cluster 真的分开
- 通过网络或高速互联传 KV Cache
- 是 `Prefill Decode Disaggregation` 更字面的实现

它强调的是：

- 不同阶段用不同 GPU 池
- 不同并行策略和 SLO 优化目标
- 接受额外的 KV 传输成本，换更强的资源专用化

### 3. 一个好记忆方式

- `解耦`：先在软件和调度语义上拆开
- `分离`：进一步在物理资源和部署层拆开

所以可以说：

> 所有 PD 分离都包含某种 PD 解耦，但不是所有 PD 解耦都走到真正的物理分离。

## 7. Prefix Caching 命中后，attention 阶段和不命中时到底差在哪

这个问题很值得准备，因为它能区分“知道概念”和“真的懂执行路径”。

### 1. 不命中 Prefix Cache 时

如果请求前缀没命中，prefill 要从头处理整段 prompt：

- 对 prompt 中每个 token 计算 `Q/K/V`
- 每层都跑完整的 causal self-attention
- 生成该段前缀对应的 KV Cache
- 最后把这些 KV 写进缓存，供后续 decode 用

这时 attention 的输入，本质是：

- 当前这段 prompt 的 hidden states
- 当前层权重
- 当前序列长度 / mask / position ids
- 输出是新的 hidden states 和新生成的 KV

### 2. 命中 Prefix Cache 时

如果前缀已经命中，区别不是“attention 还会完整跑一遍，只是更快”，而是：

**命中的那段前缀根本不用再重新做 attention 计算了。**

这时系统通常会：

- 直接把命中前缀对应的 KV Cache 接到当前请求上下文上
- 从“第一个未命中 token”开始继续 prefill
- decode 阶段直接复用“已命中前缀 KV + 新增 token KV”

所以 attention 阶段真正的差异在于：

- 不命中：需要为整段前缀重新算 `Q/K/V`
- 命中：只需要为未命中的后缀部分计算新的 `Q/K/V`

### 3. 从“传参”角度怎么说更准确

如果你问的是进入 attention kernel 的运行时状态，命中前后主要差在这些地方：

- `sequence length` 变了  
  命中后，参与本次 prefill 计算的有效新 token 长度只剩后缀长度，不再是整段 prompt 长度。

- `KV inputs` 的来源变了  
  不命中时，KV 来自本次前向现算；命中时，一部分 KV 直接来自已有 cache，另一部分才由本次前向新产生。

- `position ids / cache offsets / block table` 变了  
  因为命中前缀已经占据了前面的 cache 位置，新 token 需要接在已有 prefix 的后面，所以位置索引和 page/block 映射都从“prefix length”开始偏移。

- `attention mask` 的语义没变，但作用范围变了  
  仍然是 causal mask，但本轮实际新算的 token 只需要对“已有 prefix + 当前后缀已生成部分”做可见性约束。

### 4. 一句最面试化的回答

> Prefix Caching 命中后，不是 attention 的公式变了，而是 attention 的执行边界变了：前缀那部分不再参与本轮重算，kernel 只对未命中的后缀做增量计算，同时把已缓存的 prefix KV 当作历史上下文直接接入。

## 8. 如果把这些点串成一段完整回答

可以这样讲：

> 多卡 / 分布式通信里，我一般先按“通信原语 -> 并行策略 -> 推理调度”三层来理解。底层是 `torch.distributed + NCCL`，核心原语是 `all_reduce / all_gather / reduce_scatter / all-to-all`。`TP` 是单层内切分，所以每层高频通信，适合节点内；`MoE/EP` 的难点则主要在 token dispatch 和负载均衡，通信模式更接近 `all-to-all`。  
> 在推理侧，`Continuous Batching` 解决的是 decode iteration 级调度问题，而真正落地时必须和 `KV Cache` 分配一起看，否则 ragged batch 很难维护。单卡里 `Prefill -> Decode` 的衔接本质是前者产出 KV Cache，后者接管这个状态做增量生成。`PD 解耦` 更偏软件调度层，`PD 分离` 则进一步走到物理资源分离。再往前走，`Prefix Caching` 命中后，attention 公式不变，但命中的 prefix 不再重算，系统只对未命中的 suffix 做 prefill，并把已有 prefix KV 直接并入历史上下文。

## 9. 最后给一个高频追问清单

- `TP` 为什么更依赖节点内高速互联？
- `all_reduce` 和 `reduce_scatter + all_gather` 的关系是什么？
- `MoE` 为什么理论 FLOPs 低，实际吞吐不一定高？
- `Continuous batching` 为什么必须配合分页式 KV 管理？
- 单卡里 `prefill` 结束后，哪些状态要显式交给 `decode`？
- `PD 解耦` 为什么不一定等于 `PD 分离`？
- Prefix cache 命中后，哪些 tensor 是复用的，哪些 tensor 仍然要重新计算？
