DFlash 与 DSpark
到底怎样加速生成？

从“先猜、再验”的投机解码出发，拆解单步块扩散草稿器、半自回归顺序修正，以及为什么验证长度必须同时考虑置信度与硬件效率。

DFlash：一次并行填块 DSpark：并行 + 顺序修正 Target：最终验证者
01

先回答最容易混淆的问题

两者都借用了 diffusion-style 并行填充，但只有 DFlash 可以直接叫单步块扩散 drafter；DSpark 已经是混合式、半自回归架构。

DFlash
单步块扩散式草稿器

输入一个可靠的 anchor token 和多个 mask position，用一次 forward 同时预测整段候选。它不是图像扩散那样反复执行几十轮去噪。

DSpark
并行骨干 + 轻量顺序修正

保留 DFlash 的并行 backbone，再让 Markov/RNN head 逐位置修正 logits，并依据置信度和硬件曲线裁剪验证前缀。

一句话：DFlash 重点解决“草稿生成太串行”；DSpark 继续解决“并行草稿后缀不连贯，而且固定长度验证浪费 Target 算力”。两者最终都必须由 Target LLM 验证。
02

共同底座：投机解码是“先猜，再验”

真正昂贵的是大 Target 模型逐 token 前进。投机解码试图用便宜机制一次猜多个 token，再让 Target 用一个小 chunk forward 并行评分。

STEP 1已有 Prefix

Target 已经处理完上下文，KV Cache 可复用。

STEP 2Drafter 猜候选

便宜模型提出 y₁…yₖ，不直接写入最终输出。

STEP 3Target 并行评分

把普通 qlen=1 变成小 qlen=k 的 verification。

STEP 4连续接受

从左到右接受，遇到第一个失败位置停止。

STEP 5提交或回滚

保留通过的 KV，丢弃拒绝后缀，再进入下一轮。

一个最小例子

假设草稿器提出 4 个 token，而 Target 只认可前两个：

anchor→ draft 我喜欢苹果。
anchor→ verify 我 ✓喜欢 ✓苹果 ✗。 ✗

拒绝发生在第 3 位时，第 4 位即使“碰巧合理”也不能直接保留，因为它依赖的前缀已经改变。严格 sampling 场景还需要 speculative sampling 的接受/替代分布，才能保持 Target 分布不变。

03

DFlash：用一次 block diffusion 并行生成草稿

它不让小 drafter 自回归运行 k 次，而是把未来位置全部 mask，一次算出整个 block 的 logits。

01Target 产生 Anchor

Target 先给出一个可靠 token，同时暴露若干中间层 hidden states。

02融合 Target Context

多层 hidden 拼接、投影、RMSNorm，得到 H_ctx。

03Anchor + Masks

形如 [anchor, MASK, MASK, …] 的固定 block。

04一次并行 Forward

所有 mask position 同时产生 hidden 与 logits。

05Target Verification

Target 对候选 block 做 causal 并行评分。

06接受 + Bonus

提交最长可接受前缀，并生成替代或 bonus token。

为什么叫 diffusion-style？

  • 干净的 anchor 作为条件，未来位置以 mask 表示。
  • 一个 block 内的 mask positions 可做双向 Attention。
  • 模型学习从被 mask 的 block 恢复后续 token。

为什么又不是传统扩散模型？

  • 没有长达几十步的 noise → denoise 迭代。
  • 一次 forward 就直接输出整个 block。
  • 正确性来自 Target 验证，而不是 drafter 自身。

Target hidden 并不是简单拼到输入，而是持续注入每一层 Attention

H_ctx = RMSNorm(W_c · [H_target^(l₁); … ; H_target^(l₅)]) Q_i = W_i^Q · H_draft K_i = [W_i^K · H_ctx ; W_i^K · H_draft] V_i = [W_i^V · H_ctx ; W_i^V · H_draft]

直观理解：draft token 发出 Query，但每层都能从 Target 已编码好的语义上下文和当前 draft block 中读取 K/V。Target context 的 K/V 还可缓存并跨 drafting round 复用。

!

DFlash 的关键弱点：所有候选虽然在 block 内可以互相 Attention，但它们是同一次 forward 同时输出的，后面位置不能根据“本轮实际采样出的前一个 token”重新条件化。因此越靠后的候选越容易出现多模态冲突和 acceptance decay。

04

DSpark：先并行铺底，再顺序修正，再决定验多少

DSpark 没有放弃 DFlash 的并行优势，而是在 logits 之后增加一个远轻于 Transformer backbone 的顺序依赖通道。

01Target Context

与 DFlash 类似，提供 anchor 和语义上下文。

02并行 Backbone

一次得到所有未来位置的基础 logits U₁…Uγ。

03Sequential Head

Markov/RNN head 根据已采样前缀修正每一位。

04Confidence + STS

估计条件接受率，并校准前缀存活概率。

05硬件感知裁剪

根据 SPS(B) 给不同请求选择不同验证长度。

06Target 验证

只有选中前缀进入标准 speculative verification。

1. 顺序修正：恢复块内 token 依赖

并行 backbone 先给第 k 位一个基础 logits U_k。轻量 head 再依据已经采样的前缀加入偏置 B_k：

p_k(v | x₀, x<k) = softmax(U_k(v) + B_k(x₀, x<k, v))

默认 Markov head 只依赖前一个 token，并用低秩矩阵降低成本；RNN head 可以累计更完整的块内历史。关键要求是顺序 head 的耗时远小于并行 backbone。

2. 条件置信度：预测“这一位值得继续验吗”

c_k 估计的是：在前面 token 都被接受的条件下，第 k 位也会被 Target 接受的概率。整个前缀活到第 j 位的概率近似为：

a_j = ∏(i=1…j) c_i

乘积会随位置快速下降。原论文还使用 Sequential Temperature Scaling（STS）校准累计概率，缓解 raw confidence 过度自信。

3. Hardware-Aware Prefix Scheduler：收益与成本一起算

多验证一个 token 可能增加期望接受量，但也会增大 Target 本轮的 token batch。调度器使用预先 profile 的 SPS(B) 曲线估计不同 shape 下每秒能跑多少 verification step：

B = Σ_r (1 + l_r) τ = Σ_r (1 + Σ_j≤l_r a_r,j) Θ = τ · SPS(B)

它为每个请求贪心扩展验证前缀；只有预计能提高总吞吐 Θ 的候选才继续加入。

为什么不能只设一个固定 num_speculative_tokens？

token 1
0.96送去验证
token 2
0.91送去验证
token 3
0.78可能保留
token 4

token 5
0.19直接裁掉

这是帮助理解的示意，不是论文 benchmark。真实决策看累计前缀存活概率与具体硬件的 SPS(B)，不是简单使用固定 confidence threshold。

05

把三条路线放在一起比较

传统小模型 drafter、DFlash 与 DSpark 的差异主要在候选生成的串行深度、块内依赖，以及是否动态控制验证成本。

维度传统自回归 DrafterDFlashDSpark
生成方式y₁ → y₂ → … → yₖ一次并行预测整个 masked block并行基础 logits + 轻量顺序修正
草稿串行链长度约随 k 增长主干近似一次 forward主干并行，附加廉价顺序 head
块内真实 token 依赖天然存在缺少“按实际采样前缀再条件化”由 Markov/RNN head 恢复
Target context取决于实现多层 hidden 作为每层持久 K/V继承 DFlash 式并行 backbone
验证长度通常固定或启发式常见为固定/预设 block按 confidence + SPS(B) 动态选择
最终正确性都依赖 Target 的标准 verification / rejection sampling；drafter 不拥有最终决定权

06

工程上真正决定是否加速的因素

算法能一次猜更多 token，不等于服务系统一定更快。收益取决于 proposal、verification、KV 状态和 batch shape 的整体账本。

ACCEPTANCE

平均接受长度

草稿越准，每次昂贵 Target step 能前进越多 token。后缀接受率低时，增大 block 只会制造无效计算。

LATENCY

Drafter 自身成本

DFlash 减少串行 forward；DSpark 又加入顺序 head。新增模块必须显著便宜于省下来的 Target decode steps。

SHAPE

Verification 的硬件效率

qlen=k 的小 chunk 不总比 qlen=1 划算。并发、TP、CUDA Graph、kernel 和总 token batch 都会改变 SPS(B)。

STATE

KV Cache 提交与回滚

候选 token 会产生 speculative KV slots。接受后提交，拒绝后回滚或覆盖，不能污染后续上下文。

CALIBRATION

Confidence 是否可信

过度自信会把低价值后缀送去 Target；过度保守会提前截断本可接受的 token，浪费 drafter 能力。

SERVING

吞吐与单请求延迟并非一回事

单请求最优 block length 未必是 continuous batching 下的全局最优。DSpark 的 scheduler 正是在优化 batch 级收益。

评测时至少同时看：acceptance length、draft latency、verify latency、effective tokens per step、总吞吐、TPOT、TTFT、并发与输入/输出长度分布。只报“num speculative tokens”或单一倍数不足以解释收益。

已知事实
