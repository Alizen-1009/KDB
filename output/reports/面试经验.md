# 面试经验

## 说明

这份文档整理了大模型理论基础方向的一组高频面试题，重点覆盖 `SFT / RLHF`、`MoE`、`Transformer 架构` 与 `PPO in RLHF` 等主题。回答风格偏面试口径，强调“先给结论，再解释原因”。

## 2. SFT 和 RLHF 的训练目标在本质上有何不同？为什么大多数模型做完 SFT 之后还要再经过 RLHF 阶段？

`SFT` 的本质是监督学习，目标是最大化人工示范答案的条件似然。给定输入 `x` 和理想回答 `y`，模型学习：

$$
\max_\theta \sum_t \log \pi_\theta(y_t \mid x, y_{<t})
$$

它解决的是“模型会不会按照指令回答问题”，主要帮助模型学会：

- 指令跟随
- 任务格式
- 基本能力调用
- 更像人类标注答案的语言风格

但 `SFT` 也有明显边界：

- 同一个问题可能有很多合理答案，SFT 只能拟合训练集中出现的那种答案
- 它是逐 token 学习，不直接优化“整条回答是否更符合人类偏好”
- 对帮助性、安全性、拒答策略、风格一致性、多轮交互体验等目标表达不够直接

`RLHF` 的目标则不同。它不是继续拟合标准答案，而是借助人类偏好训练出来的奖励模型，对整条回答进行优化，目标是最大化人类更喜欢的回答的期望奖励。

因此大多数模型采用两阶段流程：

1. 先用 `SFT` 把模型训到“会回答、会跟指令走”
2. 再用 `RLHF` 把模型调到“更符合人类偏好、更稳、更适合真实产品场景”

一句话总结：

- `SFT` 解决“会不会”
- `RLHF` 解决“答得好不好、像不像人真正想要的回答”

## 3. MoE 模型中路由模块是怎样决定将 token 分配给哪些专家的？什么原因会导致专家之间的负载出现严重不均？

在 `MoE` 中，路由器会根据每个 token 的隐藏表示 `h_t` 计算一组 expert logits：

$$
z_t = W_r h_t
$$

再通过 `softmax` 得到每个 expert 的得分或概率：

$$
p_t = \text{softmax}(z_t)
$$

最后选择 `top-k` 个 expert 来处理这个 token。常见设置是：

- `top-1`：每个 token 只发给一个 expert
- `top-2`：每个 token 发给两个 expert，再对输出做加权合并

专家负载不均的常见原因有：

- 数据分布天然不均，大量 token 更偏向某些 expert 擅长的模式
- 路由器在训练早期发生塌缩，少数 expert 先占优势并形成正反馈
- 训练目标只关注主任务 loss，而没有足够强的负载均衡约束
- `top-k` 是局部贪心决策，每个 token 只选自己当前最偏好的 expert，不考虑全局容量
- 热门 expert 更容易触发 capacity 上限，进一步导致训练和路由不稳定
- 某些 expert 学成了“通用专家”，被大多数 token 优先选择

一句话总结：

`MoE` 的负载不均，本质上是“局部最优路由”和“全局资源均衡”之间的矛盾。

## 4. 当部分专家的利用率明显偏低时，可以通过哪些手段改进路由策略来提高利用率？

常见改进方式有四类。

### 1. 增加负载均衡约束

最直接的方法是在训练目标里加入：

- `load balancing loss`
- `importance loss`

这样路由器不只优化主任务效果，也会被鼓励让各 expert 的使用更均衡。

### 2. 增加路由探索性

如果 router 过早塌缩到少数 expert，可以通过以下方法增加探索：

- 给 router logits 加噪声
- 调整 softmax temperature
- 加 entropy regularization

这些方法的目标是防止早期形成不可逆的专家垄断。

### 3. 改进路由算法

除了简单的 token-level `top-k`，也可以采用更平衡的分配方式，例如：

- 从 `top-1` 改为 `top-2`
- 使用更全局的 balanced assignment
- 使用 `expert choice` 或 `sinkhorn routing` 等方法

这类方法的核心思想是：路由不应该只由 token 单方面决定，还要考虑 expert 的容量和整体分配。

### 4. 调整容量和训练机制

还可以从系统侧缓解低利用率问题，例如：

- 调大 `capacity factor`
- 减少 token drop
- 对长期低利用率 expert 做重置或再初始化
- 做 expert dropout 或其它正则，防止少数 expert 长期垄断

一句话总结：

提高低利用 expert 的使用率，核心是同时处理三件事：路由偏置、探索不足、容量约束。

## 5. 请介绍你比较熟悉的大模型架构，并从注意力计算、训练方法和推理效率等维度分析它们之间的主要差异

我比较熟悉三类架构：`Dense Decoder-only Transformer`、`MoE Transformer` 和 `Linear / Hybrid` 路线。

### 1. Dense Decoder-only Transformer

代表模型：`GPT`、`LLaMA` 系列。

注意力计算上，通常使用标准 causal self-attention，长序列下 prefill 阶段复杂度一般是 `O(n^2)`。  
训练上，所有参数对每个 token 都会激活，训练稳定性最好，生态最成熟，并行和优化手段也最完善。  
推理上，decode 依赖 `KV cache`，整体工程最成熟，但长上下文场景下 prefill 和 cache 成本都比较高。

### 2. MoE Transformer

代表模型：`Mixtral`、`DeepSeekMoE` 一类。

注意力本身通常仍是标准 Transformer attention，主要变化发生在 `FFN` 层，用多个 expert 替代单个 dense MLP。  
训练上，每个 token 只激活少数 expert，因此总参数量可以做得很大，但每 token 的激活计算量不会同比例增长。代价是要处理 router、负载均衡、`all-to-all` 通信等复杂系统问题。  
推理上，理论上 active params 较少，但如果 dispatch、batching、通信做不好，实际吞吐不一定比 dense 模型理想很多。

### 3. Linear / Hybrid / SSM 路线

代表方向：`Mamba`、一些 hybrid attention 架构、`Kimi Linear` 等。

注意力计算上，不完全依赖标准 `QK^T`，而是通过线性 attention、状态空间更新或混合结构降低长序列成本。  
训练上，长上下文场景更有潜力，但数值稳定性、kernel 设计和训练 recipe 对工程实现依赖更强。  
推理上，长上下文 prefill 通常更有优势，某些设计还能减轻 KV cache 压力，但通用生态成熟度还不如标准 Transformer。

一句话比较：

- `Dense Transformer`：最稳、最通用、生态最好
- `MoE Transformer`：参数扩展效率高，但系统复杂
- `Linear / Hybrid`：长序列效率潜力大，但实现门槛更高

## 6. PPO 在 RLHF 框架中优化的核心目标是什么？请写出其目标函数并对其中每一项进行解释

`PPO` 在 `RLHF` 中的核心目标是：

**在不让当前策略偏离参考模型太远的前提下，提高高奖励回答的生成概率。**

在 `RLHF` 中，通常先定义一个带 `KL` 惩罚的奖励：

$$
r(x, y) = r_{\text{RM}}(x, y) - \beta \, \mathrm{KL}(\pi_\theta \,\|\, \pi_{\text{ref}})
$$

其中：

- `r_RM(x, y)`：奖励模型给回答 `y` 的分数
- `\pi_ref`：参考策略，一般来自 `SFT` 模型
- `KL` 项：限制当前策略不要偏离参考策略太远
- `\beta`：平衡“追求高奖励”和“保持稳定”的权重

PPO 的核心优化目标通常写成：

$$
L^{\text{PPO}}(\theta)=
\mathbb{E}_t
\left[
\min\left(
r_t(\theta)\hat A_t,\,
\text{clip}(r_t(\theta), 1-\epsilon, 1+\epsilon)\hat A_t
\right)
\right]
$$

其中：

$$
r_t(\theta)=\frac{\pi_\theta(a_t \mid s_t)}{\pi_{\theta_{\text{old}}}(a_t \mid s_t)}
$$

各项解释如下：

- $\pi_\theta$：当前待优化的策略模型
- $\pi_{\theta_{\text{old}}}$：采样数据时使用的旧策略
- $r_t(\theta)$：新旧策略在当前动作上的概率比
- $\hat A_t$：advantage，表示该动作相对平均水平的好坏
- $\epsilon$：clip 范围，防止策略更新过猛
- $\min(\cdot)$：如果更新过于激进，就采用截断后的较小目标，保证训练稳定

实际训练时，通常还会配合：

- value loss：训练 critic 估计回报
- entropy bonus：鼓励探索
- KL penalty：继续抑制策略漂移

一句话总结：

PPO 在 RLHF 中并不是“让奖励越大越好”那么简单，而是“在稳定更新的约束下，让人类更喜欢的回答概率逐步上升”。

## 7. MoE 架构在模型参数量不断增长的背景下，为何仍能维持相对较高的训练效率？

核心原因在于：

**MoE 增加的是总参数量，但不要求每个 token 都激活全部参数。**

它之所以能保持较高训练效率，主要有四个原因。

### 1. 稀疏激活

虽然模型里有很多 expert，但每个 token 通常只激活 `top-k` 个 expert，因此每 token FLOPs 只与少数 expert 有关，而不是和总 expert 数线性增长。

### 2. 参数主要扩展在 FFN 部分

Transformer 中，FFN 往往占了很大一部分参数和算力。MoE 把 dense FFN 替换成稀疏 expert 集合后，可以显著扩大总参数量，同时控制住实际激活计算成本。

### 3. 专家天然适合并行

不同 expert 可以分布在不同设备上，因此 MoE 很适合和 expert parallelism、tensor parallelism、data parallelism 组合使用。总参数虽然大，但不需要所有参数在同一时刻、同一设备上全部参与计算。

### 4. Total params 和 active params 解耦

MoE 最大的优势是把：

- `total params`：决定模型容量
- `active params`：决定每 token 实际计算成本

这两件事拆开了。这样模型可以在不显著增加每 token 计算量的情况下，获得更大的参数容量和表示能力。

一句话总结：

MoE 的高训练效率，并不是因为它“参数多但白送”，而是因为它通过稀疏激活，把“容量扩张”和“计算扩张”部分解耦了。

## 附录：RoPE 面试追问框架

如果面试官是做 `AI infra / 模型系统 / 架构研究` 的，关于 `RoPE` 通常不会只停留在“RoPE 有什么好处”这种表层问题，而会沿着“机制理解 -> 数学直觉 -> 工程实现 -> 系统影响 -> 研究权衡”五层一路往下追。

### 1. 先看是否真正理解机制

常见追问：

- `RoPE` 和绝对位置编码最本质的区别是什么？
- 为什么说 `RoPE` 让 attention score 自然依赖相对位置，而不是绝对位置？
- 为什么 `RoPE` 通常只作用在 `Q/K` 上，而不是 `V` 上？

这一层面试官主要在看：

- 你是不是只会背“旋转位置编码”这个标签
- 你是否真的知道它本质上是在改 `Q \cdot K` 的几何关系

### 2. 再看能不能讲清数学直觉

常见追问：

- 不用公式，怎么解释为什么旋转之后会和位置差 `m-n` 有关？
- 为什么 `RoPE` 是按两维一组做旋转？
- `rope_theta` 到底控制什么？
- `partial_rotary_factor` 是什么意思？为什么有的模型不是 `1.0`？

这一层面试官主要在看：

- 你能不能把“二维旋转”“频率谱”“部分维度参与旋转”这些概念串起来
- 你是否能把数学对象和工程参数一一对应起来

### 3. 再看有没有实现感

常见追问：

- 你在 PyTorch 里会怎么实现 `RoPE`？
- 为什么通常不会真的去构造一个完整旋转矩阵？
- `rotate_half + cos/sin` 和复数乘法的实现，本质上是什么关系？
- 在多头注意力里，`RoPE` 是作用在 `head_dim` 的哪个维度上？
- 如果 `partial_rotary_factor = 0.25`，代码里会怎么切张量？

这一层面试官主要在看：

- 你是不是看过真实模型实现，而不只是论文图示
- 你能不能把公式落到 tensor shape、kernel 和代码路径上

### 4. 然后往 AI infra 方向深入

常见追问：

- `RoPE` 在 `prefill` 和 `decode` 阶段分别怎么处理？
- 有了 `KV cache` 之后，`RoPE` 是在写 cache 前做，还是读 cache 时做？为什么？
- 如果是 `paged attention` 或 `continuous batching`，`position ids` 怎么管理？
- 长上下文推理里，`RoPE` 会不会成为数值稳定性问题？通常怎么处理？
- 如果做 `int8 / fp8 / kv quant`，`RoPE` 会带来什么额外挑战？

这一层面试官主要在看：

- 你是不是“懂模型但不懂系统”
- 你是否知道位置编码会真实影响推理引擎、`KV cache`、batching、kernel 和量化设计

### 5. 最后看 research tradeoff

常见追问：

- 为什么很多模型用了 `RoPE`，长上下文还是会崩？
- `rope_theta` 调大，本质上换来了什么，又牺牲了什么？
- `ALiBi`、绝对位置编码、`RoPE` 各自的 tradeoff 是什么？
- `YaRN`、`NTK-aware scaling`、`LongRoPE` 这些方法，本质上是在修什么问题？
- 像 Gemma 这种 `Dual RoPE`，为什么 global layer 可能用更大的 `theta` 和更小的 `partial_rotary_factor`？

这一层面试官主要在看：

- 你能不能从“一个机制”上升到“一个设计空间”
- 你是否理解 `RoPE` 的边界、扩展方法和系统后果，而不是把它当成固定配方

一句话总结：

如果面试官沿这五层持续追问，真正想区分的不是“你知不知道 `RoPE` 这个名词”，而是你是否同时具备：

- 机制理解
- 数学直觉
- 实现能力
- 系统视角
- research tradeoff 意识

## 附录：简历高频八股速查

这一节整理的是更偏简历追问的高频问题，覆盖 `FlashAttention`、算子融合、性能分析工具、基础模型架构、`KV cache` 和量化里的 `per-group size`。这里默认把你提到的 `pre-group size` 理解成 `per-group quantization group size`。

### 1. FlashAttention

一句话定义：

`FlashAttention` 不是“更快的 softmax”，而是通过 `tiling + SRAM 复用 + online softmax`，在保持 exact attention 的前提下显著减少 `HBM` 读写的注意力实现。

它解决什么问题：

- 标准 attention 在长序列下不仅算得多，而且中间矩阵会频繁进出显存
- 很多场景真正的瓶颈不是 FLOPs，而是 memory traffic
- 长上下文 prefill 时这个问题尤其明显

核心机制：

- 把 `Q/K/V` 按 block 切分，在 shared memory / SRAM 里完成局部 attention
- 不显式 materialize 完整的 attention matrix
- 用 `online softmax` 在分块条件下精确合并 softmax 分子和分母
- `FA1` 重点是 IO-aware 的 exact attention
- `FA2` 进一步优化 work partition，让并行度和 GPU 利用率更高

常见追问：

- 为什么 `FlashAttention` 是 exact 而不是 approximate？
- `online softmax` 为什么可以分块计算并最后合并？
- 它优化的是 FLOPs 还是 memory traffic？
- 为什么它在长序列场景下收益更大？

面试回答要点：

- `FlashAttention` 的核心收益来自减少中间结果落到 HBM 的次数
- 它本质上是 IO 优化，不是单纯的数学近似
- decode 阶段收益通常不如 prefill 明显，因为 decode 更像小 batch 的 memory-bound 场景

### 2. 算子融合

一句话定义：

算子融合的本质是把多个本来分开的 kernel 合并执行，减少中间张量写回 global memory 和 kernel launch 开销。

它解决什么问题：

- 很多算子链是 memory-bound，不是 compute-bound
- 中间结果多次落回显存，会带来额外读写和同步成本
- 小 kernel 太多时，CPU launch 和 GPU 调度开销也会很明显

常见可融合场景：

- `bias + gelu`
- `add + layernorm / rmsnorm`
- attention 中的 `QK^T + mask + softmax + PV`
- optimizer update 链

常见追问：

- 为什么融合不一定总是更快？
- 哪些算子适合融合，哪些不适合？
- 融合的代价是什么？

面试回答要点：

- 融合可能提升吞吐，但也可能增加寄存器压力、降低 occupancy
- 融合边界要看数据依赖、访存模式和 kernel 资源占用
- “能融合”不等于“值得融合”，最终还是 benchmark 驱动

### 3. Nsight Systems 和 Nsight Compute 怎么用

一句话区分：

- `nsys` 解决“时间花在哪”
- `ncu` 解决“这个 kernel 为什么慢”

`nsys` 的用途：

- 看 CPU launch 是否有空洞
- 看 GPU kernels 是否连续
- 看 memcpy、NCCL 和计算是否重叠
- 看 prefill / decode 各阶段时间分布
- 看是不是 CPU 没有及时把工作喂给 GPU

常见命令：

```bash
nsys profile -t cuda,nvtx,osrt,cublas,cudnn -o trace python xxx.py
```

`ncu` 的用途：

- 看单个 kernel 的 SM 利用率
- 看 achieved occupancy
- 看 memory throughput、L2 / DRAM 行为
- 看 warp stall reason
- 看 bank conflict、指令分布、访存效率

常见命令：

```bash
ncu --set full --kernel-name regex:xxx python xxx.py
```

常见追问：

- 什么时候先用 `nsys`，什么时候直接上 `ncu`？
- 如何判断瓶颈是 launch、memory 还是 kernel 本身？
- 遇到一个慢 kernel，你怎么定位是 occupancy、访存还是同步问题？

面试回答要点：

- 先全局后局部：先用 `nsys` 找时间热点，再用 `ncu` 看热点 kernel 的微观指标
- 如果一上来就用 `ncu`，很容易在错误的 kernel 上过度优化

### 4. 模型基础架构

最基础的 decoder-only 语言模型骨架可以概括为：

`token embedding -> position encoding / RoPE -> N 层 decoder block -> lm head`

每层 decoder block 通常包含：

- norm
- self-attention
- residual
- norm
- MLP 或 MoE
- residual

常见延展点：

- attention 头型：`MHA / MQA / GQA`
- 长上下文机制：`RoPE / ALiBi / scaling`
- 稀疏化路径：`MoE`
- 推理优化：`KV cache / paged attention / continuous batching`

常见追问：

- dense Transformer、MoE、linear / hybrid 架构最大的差异是什么？
- `MQA/GQA` 为什么更省推理显存？
- decoder-only 为什么更适合生成式任务？

面试回答要点：

- dense 架构最稳、生态最好
- MoE 把参数扩展和激活计算部分解耦，但系统复杂
- linear / hybrid 路线更关注长序列效率，但工程成熟度更依赖具体实现

### 5. KV cache 的缓存和计算

一句话定义：

`KV cache` 是在自回归推理中缓存历史 token 的 `K/V`，避免每次生成新 token 时重复计算整段历史。

它解决什么问题：

- 如果没有 cache，每生成一个 token 都要重新计算全部历史位置的 `K/V`
- 有了 cache，新 token 只需要算自己的 `Q/K/V`，再让 `Q` 去和历史 `K/V` 做 attention

显存计算常用公式：

$$
\text{KV cache bytes}
=
B \times S \times L \times H_{kv} \times D \times 2 \times \text{dtype\_bytes}
$$

其中：

- $B$：batch size
- $S$：sequence length
- $L$：layer 数
- $H_{kv}$：KV heads 数
- $D$：head dim
- $2$：`K` 和 `V` 两份
- $\text{dtype\_bytes}$：每个元素字节数，例如 `fp16 / bf16 = 2`

常见追问：

- 为什么 `GQA / MQA` 更省 cache？
- prefill 和 decode 阶段，`KV cache` 的压力为什么不一样？
- `paged attention` 为什么能缓解大 batch 和长上下文下的显存碎片问题？

面试回答要点：

- prefill 更像大矩阵吞吐问题
- decode 更像 memory / cache / 调度问题
- 长上下文推理里，很多时候先卡住的不是算力，而是 `KV cache`

### 6. per-group quantization group size 怎么选

一句话定义：

`group size` 是量化时一组权重共享同一套 scale / zero-point 的分组粒度，它本质上是精度和吞吐之间的折中参数。

一般规律：

- group size 小，例如 `32 / 64`
  - 量化更细，误差更小
  - 但元数据更多，访存和 kernel 更复杂
- group size 大，例如 `128 / 256`
  - 元数据更少，吞吐更友好
  - 但量化误差通常更大

常见工程经验：

- `int4 weight-only` 常见 `group size = 128`
- 更保守时会选 `64`
- 更追求吞吐时可能选 `256`

常见追问：

- 为什么 `group size` 不是越小越好？
- 为什么某些 kernel 对特定 group size 更友好？
- 激活量化和权重量化对 group size 的敏感度有什么不同？

面试回答要点：

- group size 不是纯数学问题，还和 memory layout、向量化宽度、tile 对齐、kernel 实现绑定
- 选型通常是“误差可接受 + kernel 友好 + benchmark 最优”的综合结果

一句话总结：

简历里的这类八股，最好的回答方式不是只背定义，而是按统一结构去讲：

1. 它是什么  
2. 它解决什么问题  
3. 它怎么做  
4. 它的 tradeoff 是什么  
5. 工程上怎么验证它真的有效

### 7. CUDA Graphs：为什么快，以及为什么难用

一句话定义：

`CUDA Graphs` 的目标是把一段稳定的 GPU 工作流提前 capture 成图，后续 replay 时通过一次 API 调用直接提交整段执行，从而显著减少 CPU launch 开销和 GPU bubble。

为什么它会快：

- 传统执行模式下，CPU 会逐个 launch kernel，GPU 跑完一个 kernel 之后还要等 CPU 发下一个
- `CUDA Graphs` 会把这段固定的工作流提前录下来，replay 时 GPU 可以 back-to-back 执行整段 kernel
- 对重复结构非常稳定的训练 / 推理循环，这能明显减少 launch overhead

按你提供的 `GTC 2026` keynote 笔记，一个比较有代表性的结论是：

- `LoRA 70B` 在 `512` 卡训练上，`CUDA Graphs` 路线曾报告约 `2.75x` 加速

为什么难用：

真正难的地方不是 API 本身，而是它要求你满足一套非常严格的执行约束。最核心的两条可以概括为：

- capture 时，GPU 侧工作流要稳定，不能混入不支持的 API 或动态行为
- replay 时，kernel 参数和很多底层地址关系都默认被固定下来，输出通常会持续写回同一批内存地址

这两条约束会引出很多非常反直觉的 bug。

#### 经典坑 1：DataLoader 的 `pin_memory` 破坏 capture

问题本质：

- `cudaHostAlloc()` 在 capture 期间通常属于 unsupported API
- 如果它从任意线程触发，都可能导致 graph capture 失败

常见修法：

- 用 `capture_error_mode="thread_local"`
- 同时关闭 autograd 的多线程行为，避免别的线程在 capture 期间偷偷触发 host alloc

面试回答要点：

- `CUDA Graphs` 对 host-side alloc 很敏感
- 不是只有“当前线程里的 CUDA 代码”要干净，旁路线程也可能把 capture 搞炸

#### 经典坑 2：warmup 迭代的 autograd 引用没有清掉

问题本质：

- warmup 里产生的 `loss tensor` 还活着
- 它挂着上一轮的 `AccumulateGrad` 节点
- capture 时如果牵扯到 default / NULL stream，就可能因为 stream join 关系报错

常见修法：

- warmup 结束后显式 `del loss`
- 或者让 warmup 在独立 stream 上完成，和正式 capture 路径隔开

面试回答要点：

- `CUDA Graphs` 常见 bug 不是“当前这一轮写错了”，而是上一次迭代的引用还没死干净

#### 经典坑 3：学习率是 Python float，导致 replay 时不更新

问题本质：

- 如果 `lr` 只是 Python float，它不会以设备张量的形式进入 graph
- replay 时实际 kernel 里看到的还是 capture 当时那份值
- 最后可能表现成 loss 曲线明显劣化，但表面看不出哪里错了

常见修法：

- 把学习率写成设备张量，例如 `lr = torch.tensor(0.1, device="cuda")`

面试回答要点：

- graph 里真正会 replay 的，是 capture 时那批设备侧参数和地址，不是 Python 解释器后续看到的高层对象变化

#### 经典坑 4：use-after-free，训练直接发散

问题本质：

- 把 `lr` 从 Python float 改成 tensor 之后，如果你写 `lr = lr * 0.9`
- 这通常会分配一个新的 tensor
- 原来那块内存可能已经被释放或复用
- 但 graph replay 的 kernel 仍然引用旧地址

常见修法：

- 用原地更新，比如 `lr.mul_(0.9)`，保证地址不变
- 打开 `check_input_liveness=True` 帮助发现这类问题

面试回答要点：

- `CUDA Graphs` 的一个核心心智模型是：**地址稳定比对象名稳定更重要**

#### 经典坑 5：数据依赖的控制流破坏 capture

问题本质：

- 如果控制流依赖运行时数据，很容易在 capture 期间触发 `cudaStreamSynchronize` 之类 unsupported API
- 这类动态图行为本来就和“录制固定执行图”天然冲突

常见修法：

- 非侵入式路线是使用 `torch.cond()`
- 你笔记里提到 PyTorch `2.12` 引入了 `CUDA Graph Conditional Node`，可以把条件分支留在同一个 graph 里，而不需要手工把图拆成多段

面试回答要点：

- `CUDA Graphs` 最适合稳定、重复、形状和执行路径都相对固定的工作流
- 动态控制流越重，capture 越容易碎

#### 最低成本的入场方式

如果不想手写完整 `CUDA Graphs` 生命周期，一个更实际的入场方式是：

```python
torch.compile(mode="reduce-overhead")
```

它的思路是：

- 能 graph capture 的部分尽量自动 capture
- 不适合 capture 的部分自动回退到普通 eager 执行

优点：

- 接入门槛低
- 不需要你手动维护每一段 capture / replay 逻辑

代价：

- graph break 太多时，收益会明显缩水
- 很多第三方库或自定义路径还未必完全兼容 `compile`

一句话总结：

`CUDA Graphs` 的性能潜力很强，但真正难的不是“会不会开”，而是你是否理解 capture / replay 对地址稳定性、控制流、host alloc、autograd 引用和输入生命周期的全部约束。
