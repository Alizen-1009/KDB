# Recursive Language Models 中文导读

## 这篇文章在讨论什么

这篇文章讨论的不是怎样把 Transformer 的原生上下文窗口从 128K 扩到 1M，也不是提出一种新的递归神经网络。它关心的是另一个层面的问题：**当 Agent 连续工作几天、几周，产生的历史、工具输出和中间状态远远超过模型上下文窗口时，系统应该怎样组织这些信息？**

作者的出发点是，长上下文存在两类成本：

1. 上下文越长，每生成一个新 token 要处理的历史越多，推理成本随之上升。
2. 即使上下文仍在模型标称窗口内，模型也可能发生 `context rot`：重要信息被大量无关细节稀释，检索和推理能力下降。

Claude Code、Codex 等 Agent 通常用文件系统保存状态，并定期把历史对话总结成较短上下文。文章认可这种方式，但提出了更一般的 [[../../wiki/concepts/Context Folding|Context Folding]] 视角：Agent 不必被动接受一条不断增长的上下文，而可以主动决定哪些信息留在当前窗口、哪些信息折叠到外部、何时重新读取。

## RLM 到底是什么

[[../../wiki/concepts/Recursive Language Model|Recursive Language Model]]（RLM）可以理解成“一个负责调度的主模型 + 一个持久 Python 工作区 + 若干拥有全新上下文的子模型”。

它的基本工作方式是：

```text
超长原始数据
    ↓ 不直接塞进主模型 prompt
Python 变量 / 文件 / 数据结构
    ↓ 主模型写代码检索、分块、过滤
局部数据片段
    ↓ llm_batch() 并行委派
多个 fresh sub-LLM
    ↓ 返回局部发现
主模型聚合、检查、继续查询
    ↓
answer["content"] → 最终答案
```

这里的“recursive”不是说一个网络层递归执行，而是模型可以调用新的模型实例处理子问题。文章中的实现实际上只有一层递归：主模型能调用 sub-LLM，sub-LLM 不能继续调用下一层 sub-LLM。

## Prime Intellect 版本的几个关键设计

### 1. 大输入默认不可见

用户的任务描述进入主模型上下文，但额外的大规模数据只放在 Python 环境中。主模型必须写代码才能读取它。单次 REPL 输出默认又限制为 8192 字符，因此模型不能简单地把全部数据重新打印进上下文，而需要先搜索和过滤。

### 2. 工具只给子模型

网页搜索和文件读取经常产生几万甚至上百万 token。Prime Intellect 的实现不让主 RLM 直接调用这些工具，而是把工具交给 sub-LLM。子模型消化冗长输出后，只向主模型返回较短的结果，从而保护主模型上下文。

这是一种**上下文隔离**：不是减少整个系统消耗的 token，而是让冗长 token 停留在短生命周期的子上下文中。

### 3. 子模型可以并行

主模型可以通过 `llm_batch()` 同时提交多个 prompt。例如处理长访谈记录时，可以让不同 sub-LLM 分别扫描不同分块，再由主模型汇总。它适合信息抽取、分类、检索等可分解任务，但对依赖一条紧密推理链的问题未必有利。

### 4. 最终答案可以反复修改

模型不必一次性输出答案，而是不断编辑 `answer["content"]`；只有设置 `answer["ready"] = True`，rollout 才会结束。这使精确复制、格式检查和局部修订更自然。

## 四组实验分别说明什么

### DeepDive：工具隔离是否有效

DeepDive 需要连续网页搜索和证据拼接，工具输出很长。默认 RLM 并没有稳定胜过标准 LLM；只有明确提示它“拆问题、并行委派、交叉验证、继续补缺口”后，效果才改善。

这说明 scaffold 提供了能力，但未经过针对性训练的模型未必知道怎样使用。环境提示本身也是重要变量。

### math-python：复杂 scaffold 可能让简单任务退化

标准模型已经熟悉普通 Python tool。换成 RLM 后，GPT-5-mini 思考得更久、主模型 token 更多，但准确率下降。即使提示它调用 sub-LLM 验证，也没有改善。

这构成文章最重要的反例：**RLM 不是免费增强，也不是所有任务都适合多 Agent 分解。** 额外的控制接口可能干扰模型原本熟悉的求解策略。

### Oolong：RLM 的核心长上下文场景

Oolong 要从很长的数据中重复抽取、分类并聚合信息。RLM 可以用 Python 正则直接处理结构化标签，也可以把复杂真实记录分块交给 sub-LLM。

文章称，在最重要的 `real` 子集上，RLM 在约 1.5M 字符（文中估算约 300–400K token）附近明显优于标准 LLM。与此同时，简单的 synthetic 数据未必受益，过度依赖 sub-LLM 反而可能降低表现。

这个结果不能直接当成公平的长上下文模型排名：实验每种设置只抽样 50 个任务，而且标准 LLM 的部分超长输入被 API 直接拒绝，导致两边看到的难度分布不完全一致。

### Verbatim-copy：变量式答案的价值

普通 LLM 只能一次性生成要复制的字符串；RLM 可以先写入答案变量，再打印检查，用字符串替换修正错误。GPT-5-mini 在多数内容类型上受益，但代价是更多轮次、更高延迟和更多 token。

这说明 RLM 的收益不只来自 sub-LLM，也来自“语言模型 + 确定性程序操作”的组合。

## 怎样理解文章中的 token 效率

文章重点区分：

- **主模型 token**：主 RLM 自己持续携带的上下文；
- **sub-LLM token**：被委派到各个短生命周期调用中的 token；
- **总 token 与 wall-clock time**：整个系统真正支付的成本。

RLM 经常显著缩短主模型上下文，却使用更多 sub-LLM token，并增加端到端时间。因此它不是传统意义上的无损压缩，而是一次计算重构：

> 把一个越来越长、越来越混乱的单一上下文，换成一个较短的控制上下文，以及许多按需创建、可并行、用完即弃的局部上下文。

这种交换对长周期一致性可能有价值，但是否省钱取决于任务分解、并行度、模型价格和子调用数量。

## 它与长上下文 Attention 的关系

文章最后强调，两条路线不是二选一：

- 长上下文 Attention 改善一次模型 forward 能处理多少历史、怎样高效关注历史；
- Context Folding/RLM 决定当前这次 forward 到底应该看到哪些历史。

前者延缓上下文退化，后者把 Agent 的外部工作记忆扩展到窗口之外。真正持续数周或数月的 Agent 可能同时需要两者。

## 阅读时需要保留的质疑

### 已知实现事实

- Prime Intellect 已在 [[../../wiki/entities/verifiers|verifiers]] 中实现实验性 `RLMEnv`。
- 当前版本支持 Python REPL、sub-LLM、批量调用、工具隔离和答案变量。
- 文章确实观察到任务和模型之间高度不一致的结果，并报告了时延与 token 代价。

### 实验观察

- 复杂长上下文和高 token 工具任务更可能受益。
- 简单任务、数学任务或模型不熟悉 scaffold 时可能退化。
- 环境提示可能显著改变结果，甚至在不同模型上产生相反效果。

### 作者假设，尚未证明

- 通过强化学习训练后，模型会稳定学会最优的上下文管理策略。
- 任意递归深度会进一步提高能力而不会造成成本和协调失控。
- RLM 将成为“2026 的范式”，并支撑持续数周到数月的 Agent。

## 一句话总结

这篇文章真正有价值的观点不是“再套一层 LLM 就会更强”，而是：

> 对长周期 Agent 来说，上下文应该被视为稀缺的运行时资源；模型不仅要在上下文里推理，还要学习如何编程式地构造、隔离、检索和回收自己的上下文。
