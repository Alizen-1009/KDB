上周，我们在 Claude Code 中发布了动态工作流（dynamic workflows）。这里的 dynamic workflow，是指在运行时针对手头任务生成并执行专用编排逻辑的工作流。Claude 现在可以即时编写自己的代理运行框架（Harness），也就是包裹模型、工具、上下文与调度逻辑的执行外壳，并为当前任务量身定制。

虽然 Claude Code 的默认 Harness 是为编码而构建的，但它对许多其他类型的任务同样有用，因为事实证明，很多任务都很像编码任务。不过，对某些类别的任务，为了达到最佳表现，我们一直需要在 Claude Code 之上构建定制 Harness，例如研究（Research）、安全分析、代理团队（agent teams）或代码审查（Code Review）。

工作流让你能够在 Claude Code 之上动态创建 Harness，使 Claude 可以更原生地解决上述所有问题。你也可以与他人共享并复用这些工作流。

本文会介绍我最初使用工作流的经历与收获，帮助你充分利用它们。请记住，最佳实践仍在发展中：动态工作流往往会使用更多 token，最适合复杂且高价值的任务。

示例提示词

在深入技术细节之前，我想先用几条示例提示词开场，帮助你思考工作流的各种可能性：

“这个测试大概每 50 次运行会失败 1 次。搭建一个工作流来复现它。围绕这个竞态提出彼此竞争的理论，而且在证据只支持其中一个理论之前不要停下。”

“使用工作流，检查我最近 50 个会话，挖掘那些我反复做出的纠正，并把反复出现的内容变成 CLAUDE.md 规则。”

“使用工作流，深入检查过去六个月 Slack 中的 #incidents，找出那些反复出现、却没有人提交工单的根因。”

“拿我的商业计划跑一个工作流，让不同的 agent 分别从投资者、客户和竞争对手的视角把它彻底批判一遍。”

“这里有一个包含 80 份简历的文件夹。使用工作流，按后端职位的要求对它们排序，并复核排名前十的简历。请用 AskUserQuestion 工具采访我，以确定评判标准。”

“我需要给这个 CLI 工具起名。使用工作流集思广益，提出一批候选项，再通过锦标赛选出前三名。”

“使用工作流，把我们的 User model 在所有地方都重命名为 Account。”

“使用工作流检查我的博客文章草稿，并对照代码库验证每一项技术主张；我不想发布任何错误内容。”

动态工作流如何运作

动态工作流会执行一个 JavaScript 文件，其中包含几个特殊函数，用来生成并协调子代理（subagents）。subagent 是拥有独立上下文和聚焦目标、由主流程派生出来执行子任务的 agent：

动态工作流也包含 JSON、Math 和 Array 等标准 JavaScript 功能，以帮助处理数据。

尤其值得了解的是，动态工作流可以决定一个 agent 使用哪个模型，以及 subagent 是否在自己的 Git 工作树（worktree，即与其他任务隔离的独立检出目录）中运行，让 Claude 能够选择任务所需的智能水平与隔离程度。

如果工作流被中断——例如用户主动中断或退出终端——恢复会话后，工作流可以从中断处继续。

为什么要用动态工作流

当你要求 Claude Code 的默认 Harness 执行一项任务时，它需要在同一个上下文窗口中同时完成规划和执行。对许多编码任务而言，这种方式非常有效，但面对长时间运行、大规模并行、高度结构化和／或对抗性的任务时，它可能失效。

原因在于：Claude 在单个上下文窗口中处理复杂任务的时间越长，就越容易出现几种特定的失败模式：

  • 代理式懈怠（agentic laziness）：Claude 在完成一项格外复杂、包含多个部分的任务之前就停下来，并在只取得部分进展后宣称工作已经完成。例如，在一次安全审查的 50 个项目中只处理了 35 个。
  • 自我偏好偏差（self-preferential bias）：Claude 倾向于偏爱自己产出的结果或发现，尤其是在被要求依据某项量规验证或评判这些结果时。
  • 目标漂移（goal drift）：经过许多轮交互后，任务逐渐失去对原始目标的忠实度，尤其是在上下文压缩之后。每一步摘要都会造成信息损失，边界情况要求或“不要做 X”之类的约束可能会丢失。

创建工作流有助于应对这些问题：它会编排相互分离的 Claude subagent，让每个 subagent 拥有自己的上下文窗口以及聚焦、隔离的目标。

动态工作流与静态工作流

你此前可能已经使用 Claude Agent SDK 或 claude -p 创建过静态工作流，用来协调多个 Claude Code 实例。

但由于静态工作流需要覆盖所有边界情况，它们通常更加通用。借助 Claude Opus 4.8 和动态工作流，Claude 现在已经足够智能，能够为你的用例编写量身定制的 Harness。

使用动态工作流时有帮助的模式

只要直接要求 Claude 创建工作流，你就可以开始使用动态工作流；也可以使用触发词 ultracode，以确保 Claude Code 创建一个工作流。

不过，为动态工作流的运作方式建立一套心智模型，会帮助你理解何时使用它们，以及如何通过提示词给 Claude 适当引导。

分类后行动（Classify-and-act）

使用一个分类器 agent 判断任务类型，再根据任务类型路由到不同的 agent 或不同的行为。也可以在流程末尾使用分类器来决定输出。

扇出并综合（Fan-out-and-synthesize）

把一项任务拆成许多更小的步骤，为每个步骤运行一个 agent，然后综合这些结果。这里的扇出（fan-out）是指把工作并行分派给多个独立执行单元。这种模式尤其适合存在大量较小步骤的情况，或每个步骤都能从独立、干净的上下文窗口中受益，从而避免相互干扰或交叉污染的情况。综合步骤是一道屏障：它会等待所有 fan-out agent 完成，再把它们的结构化输出合并为一个结果。

对抗式验证（Adversarial verification）

对每个被派生出来的 agent，再派生一个独立 agent，依据量规或标准对其输出进行对抗式验证（adversarial verification，即主动寻找错误、反例与不满足标准之处的独立复核）。

生成并过滤（Generate-and-filter）

围绕某个主题生成一批想法，再依据量规或验证结果过滤它们，去除重复项，只返回质量最高且经过检验的想法。

锦标赛（Tournament）

不是拆分工作，而是让 agent 围绕同一项工作展开竞争。派生 N 个 agent，让它们分别采用不同方法尝试同一任务。随后，由提示词或模型通过一个裁判 agent 对结果进行成对评判，直到选出胜者。

循环直至完成（Loop until done）

对于工作量未知的任务，不要预设固定轮数；改为循环派生 agent，直到满足停止条件——例如不再出现新发现，或日志中不再有错误。

用例

请创造性地思考何时以及如何要求 Claude Code 创建动态工作流。我发现，工作流有时在非技术工作中甚至更有用。

迁移与重构

Bun 使用工作流完成了从 Zig 到 Rust 的重写。你可以在 Jarred 的 X 帖子串中进一步了解具体做法，也可以查看我们如何在百万行级代码库上执行 AI 代码迁移。

关键是把任务拆成一系列需要逐项处理的步骤，例如调用点、失败的测试、模块等。针对每个修复，在一个 worktree 中派生 subagent 完成修改；再让另一个 agent 进行对抗式审查，最后合并这些修改。可以考虑明确要求 agent 不要使用资源密集型命令，这样你就能尽可能提高并行度，而不会耗尽本机资源。

深度研究

我们在 Claude Code 内发布了一个使用动态工作流的深度研究 skill（/deep-research）。具体来说，它会 fan-out 多项网页搜索、获取来源、对来源中的主张进行对抗式验证，并综合生成一份带引文的报告。

不过，这类研究不只适用于网页搜索。例如，你可以要求 Claude 根据 Slack 中的上下文汇编状态报告，或通过深入探索代码库来研究某项功能的工作方式。

排序

你可能有一个项目列表，想依据某种你认为 Claude Code 擅长评估的定性指标对它排序，例如按 bug 严重程度排列支持工单。但是，如果你试图在一个提示词中对 1000 多行数据排序，质量会下降，而且内容无法装入上下文。作为替代，可以运行锦标赛、搭建由成对比较 agent 组成的流水线（比较判断比绝对评分更可靠），或先并行分桶排序再合并。每次比较都由独立 agent 完成，因此确定性的循环负责维护对阵结构，只有当前运行顺序留在上下文中。

记忆与规则遵循

原文配图｜所在小节：“记忆与规则遵循”。为保持 HTML 自包含，此处不加载原文远程图片，也不对图片细节作推测性描述。

如果你有一组 Claude 经常漏掉或难以遵循的特定规则，即使把这些规则写入 CLAUDE.md 也无济于事（原文此处写作 CLAUDE.mds），那么可以创建一个工作流，列出必须由验证 agent 检查的规则——每条规则对应一个验证者。再创建一个持怀疑态度的人格 subagent 来审查这些规则、确认它们是否合理，有助于避免出现过多误报。

反向操作也同样可行：从最近的会话和代码审查评论中挖掘你反复做出的纠正，让并行 agent 对它们聚类，对每个候选规则进行对抗式验证（这条规则真的能够避免一次实际错误吗？），然后把通过筛选的规则提炼回 CLAUDE.md。

根因调查

调试的最佳做法，是提出几个彼此独立的假设并逐一检验；但如果你只使用一个上下文窗口，Claude 可能陷入自我偏好偏差。

工作流可以在结构上阻止这种情况：派生多个 agent，让它们从互不重叠的证据中生成假设。例如，可以分别为日志、文件和数据设置独立 agent。随后，每个假设都可以交由一组验证者与反驳者审视。

这不只适用于代码。工作流可以用于销售（为什么三月份的销售额下降了？）、数据工程（为什么这条流水线失败了？）或任何事后复盘。

规模化分诊

原文配图｜所在小节：“规模化分诊”。为保持 HTML 自包含，此处不加载原文远程图片，也不对图片细节作推测性描述。

每个团队都有支持队列、bug 报告或某种其他积压事项，人类无法把它们全部处理完。

分诊工作流会对每个项目分类，与已经跟踪的事项去重，然后采取行动。这可能意味着尝试修复，也可能意味着升级给人类用户处理。

隔离（quarantine）是分诊工作流的一种实用模式。它禁止那些读取不受信任公开内容的 agent 执行高权限操作；这些高权限操作改由负责根据信息采取行动的 agent 完成。

把分诊工作流与 /loop 结合起来，让 Claude 持续执行这项工作。

探索与品味

当你需要探索一个解决方案的不同路径时，工作流会很有用；尤其是设计或命名这类依赖品味、又能从量规中受益的问题。

可以尝试要求 Claude 探索一批解决方案，并为审查 agent 提供一套关于优秀方案应具备哪些特征的量规。当审查 agent 认为方案已经满足标准时，任务才算完成。也可以依据这套量规，通过锦标赛对方案进行排序或选择。

评测（Evals）

你可以为特定任务运行轻量评测：在 worktree 中派生独立 agent，再派生比较 agent，依据量规比较并评定具体输出。例如，可以先评估你创建的一项 skill 是否符合特定标准，再据此加以改进。

模型与智能路由

创建一个针对你的任务调优的分类器 agent，由它决定使用哪个模型。当任务会涉及许多工具调用时，这种做法很有帮助：在执行之前先开展研究，可以确定最适合这项工作的模型。

例如，对于“解释 auth 模块如何工作”这项任务，最佳模型取决于 auth 模块包含多少文件以及代码库的整体形态。分类器 agent 可以完成这项研究，再根据任务的预期复杂度把它路由给 Sonnet 或 Opus。

何时不应使用动态工作流

限制与成本：工作流仍是新事物。虽然在许多用例中，它们能够带来超出常规水平的结果，但并非每项任务都需要工作流，而且工作流最终可能使用多得多的 token。

最好以创造性的方式使用工作流，推动 Claude Code 去完成你以前没有尝试过的事情。对于常规编码任务，请试着问自己：它真的需要更多算力吗？例如，大多数传统编码任务并不需要一个由 5 名审查者组成的评审组。

同样的判断也适用于更高一层的架构层面：多 agent 与单 agent 的选择遵循相似逻辑——并行与专业化必须证明，其收益足以覆盖协调成本。

构建动态工作流的技巧

提示词设计

在动态工作流的提示词中写得足够详细，并使用上文介绍的具体技术，能够取得最佳结果。

工作流并不只适用于大型任务。你可以提示模型使用“快速工作流（quick workflow）”。例如，你可以针对某项假设创建一次快速的对抗式审查。

与 /goal 和 /loop 结合

当工作流可以重复执行时——例如分诊、研究或验证——可将它与 /loop 结合，以固定间隔运行；再使用 /goal 设置一项硬性的完成要求。

Token 使用预算

你可以为动态工作流设置明确的 token 使用预算，以限制一项任务消耗的 token 数量。可以在提示词中给出类似“use 10k tokens”的预算，这会设置使用上限。

保存与共享动态工作流

你可以在工作流菜单中按下“s”来保存工作流。可以把它们签入 ~/.claude/workflows，也可以通过 skill 分发。
