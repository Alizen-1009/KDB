Introduction引言

Skill（技能）是一组指令——封装成一个简单的文件夹——用于教 Claude 如何处理特定任务或工作流。Skill 是根据你的具体需求定制 Claude 的最强大方式之一。你不必在每次对话中重新解释自己的偏好、流程和领域专长，而可以只教 Claude 一次，并在之后每次使用时持续受益。

当你有可重复的工作流时，Skill 尤其有用：根据规格生成前端设计、以一致的方法开展研究、创建符合团队风格指南的文档，或编排多步骤流程。Skill 能很好地配合 Claude 的内置能力，例如代码执行和文档创建。对于构建 MCP 集成的人，Skill 还增加了另一层强大能力，帮助把原始的工具访问转变为可靠且经过优化的工作流。

本指南涵盖构建有效 Skill 所需了解的一切——从规划与结构，到测试与分发。无论你是为自己、团队还是社区构建 Skill，都能在全文中找到实用模式和真实案例。

你将学到什么

  • Skill 结构的技术要求与最佳实践
  • 独立 Skill 与 MCP 增强工作流的模式
  • 我们观察到在不同用例中表现良好的模式
  • 如何测试、迭代和分发 Skill

本指南面向谁

  • 希望 Claude 始终如一地遵循特定工作流的开发者
  • 希望 Claude 遵循特定工作流的高级用户
  • 希望在组织内标准化 Claude 工作方式的团队
阅读本指南的两条路径

构建独立 Skill？重点阅读“基础知识”“规划与设计”以及类别 1–2。增强 MCP 集成？“Skills + MCP”小节和类别 3 适合你。两条路径共享同一套技术要求，但你可以选择与自身用例相关的内容。

读完本指南你将获得什么：到最后，你将能够在一次集中工作中构建出一个可用的 Skill。使用 skill-creator 构建并测试第一个可工作的 Skill，预计需要约 15–30 分钟。

现在开始吧。

Chapter 1 · Fundamentals基础知识

什么是 Skill？

一个 Skill 是包含以下内容的文件夹：

  • SKILL.md（必需）：采用 Markdown 编写、带 YAML frontmatter（文档头部元数据）的指令
  • scripts/（可选）：可执行代码（Python、Bash 等）
  • references/（可选）：按需加载的文档
  • assets/（可选）：输出中使用的模板、字体、图标

核心设计原则

Progressive disclosure（渐进式披露）

Skill 使用三级系统：

  1. 第一级（YAML frontmatter）：始终加载进 Claude 的系统提示词。它提供刚好足够的信息，让 Claude 知道每个 Skill 应在何时使用，而无需把全部内容都载入上下文。
  2. 第二级（SKILL.md 正文）：当 Claude 认为该 Skill 与当前任务相关时加载。包含完整指令与指导。
  3. 第三级（链接文件）：Skill 目录中捆绑的其他文件，Claude 可仅在需要时选择浏览和发现。

这种渐进式披露在保留专业能力的同时，将 token 使用量降到最低。

可组合性（Composability）

Claude 可以同时加载多个 Skill。你的 Skill 应能与其他 Skill 良好协作，不要假定它是当前唯一可用的能力。

可移植性（Portability）

Skill 在 Claude.ai、Claude Code 和 API 中的工作方式相同。只需创建一次，即可无需修改地用于所有界面，前提是相应环境支持该 Skill 所需的依赖。

面向 MCP 构建者：Skills + Connectors

提示：正在构建不使用 MCP 的独立 Skill？可直接跳到“规划与设计”——之后随时可以回来阅读。

如果你已经有一个可工作的 MCP 服务器，那么最难的部分已经完成。Skill 是叠加在它之上的知识层——捕获你已经掌握的工作流与最佳实践，让 Claude 能够一致地应用它们。

厨房类比

MCP 提供专业厨房：能够使用工具、食材和设备。

Skill 提供菜谱：说明如何一步步创造有价值成果的指令。

两者结合，用户就能完成复杂任务，而不必亲自弄清每一个步骤。

两者如何协同工作

MCP（连接能力）Skills（知识）
将 Claude 连接到你的服务（Notion、Asana、Linear 等）教 Claude 如何有效使用你的服务
提供实时数据访问和 tool call（工具调用）捕获工作流与最佳实践
Claude 能做什么Claude 应该怎样做

为什么这对 MCP 用户很重要

没有 Skill

  • 用户连接 MCP 后不知道下一步做什么
  • 支持工单不断询问“如何用你们的集成做 X”
  • 每次对话都从头开始
  • 用户每次提示方式不同，导致结果不一致
  • 实际问题是缺少工作流指导，用户却责怪连接器

有 Skill

  • 预构建工作流在需要时自动激活
  • 工具使用一致、可靠
  • 每次交互都内置最佳实践
  • 集成的学习门槛更低

Chapter 2 · Planning and design规划与设计

从用例开始

在编写任何代码之前，先确定你的 Skill 应支持的 2–3 个具体用例。

良好的用例定义：

Use Case: Project Sprint Planning
Trigger: User says "help me plan this sprint" or "create
sprint tasks"
Steps:
1. Fetch current project status from Linear (via MCP)
2. Analyze team velocity and capacity
3. Suggest task prioritization
4. Create tasks in Linear with proper labels and estimates
Result: Fully planned sprint with tasks created

问问自己：

  • 用户想完成什么？
  • 这需要哪些多步骤工作流？
  • 需要哪些工具（内置工具或 MCP）？
  • 应嵌入哪些领域知识或最佳实践？

常见 Skill 用例类别

在 Anthropic，我们观察到三种常见用例：

类别 1：文档与资产创建（Document & Asset Creation）

用于：创建一致、高质量的输出，包括文档、演示文稿、应用、设计、代码等。

真实案例：frontend-design Skill（另请参阅用于 DOCX、PPTX、XLSX 和 PDF 的 Skill）

“创建具有鲜明特色、达到生产级质量且设计水准很高的前端界面。用于构建 Web 组件、页面、产物、海报或应用程序时。”

关键技术：

  • 嵌入式风格指南与品牌标准
  • 用于保持输出一致的模板结构
  • 最终定稿前的质量检查清单
  • 无需外部工具——使用 Claude 的内置能力

类别 2：工作流自动化（Workflow Automation）

用于：从一致方法论中受益的多步骤流程，包括跨多个 MCP 服务器的协调。

真实案例：skill-creator Skill

“用于创建新 Skill 的交互式指南。引导用户完成用例定义、frontmatter 生成、指令编写和验证。”

关键技术：

  • 带验证关卡的逐步工作流
  • 适用于常见结构的模板
  • 内置审查与改进建议
  • 迭代优化循环

类别 3：MCP 增强（MCP Enhancement）

用于：提供工作流指导，以增强 MCP 服务器所提供的工具访问。

真实案例：sentry-code-review Skill（来自 Sentry）

“利用 Sentry MCP 服务器提供的错误监控数据，自动分析并修复 GitHub Pull Request 中检测到的缺陷。”

关键技术：

  • 按顺序协调多次 MCP 调用
  • 嵌入领域专长
  • 提供原本需要用户自行说明的上下文
  • 处理常见 MCP 问题的错误

定义成功标准

你如何判断 Skill 是否有效？

以下是期望目标——属于粗略基准，而不是精确阈值。应追求严谨，但也要接受其中会包含一定程度的“凭感觉评估”。我们正在积极开发更稳健的衡量指导和工具。

定量指标：

  • Skill 能在 90% 的相关查询上触发
    • 衡量方法：运行 10–20 条本应触发 Skill 的测试查询。记录其中有多少次自动加载，多少次需要显式调用。
  • 在 X 次 tool call 内完成工作流
    • 衡量方法：比较启用和不启用 Skill 时完成同一任务的情况。统计工具调用次数和消耗的 token 总量。
  • 每个工作流 0 次 API 调用失败
    • 衡量方法：在测试运行期间监控 MCP 服务器日志。跟踪重试率与错误代码。

定性指标：

  • 用户不需要提示 Claude 下一步怎么做
    • 评估方法：测试期间记录你需要重定向或澄清的频率。向 beta 用户收集反馈。
  • 工作流无需用户纠正即可完成
    • 评估方法：对同一请求运行 3–5 次。比较输出在结构一致性和质量方面的表现。
  • 跨会话结果一致
    • 评估方法：新用户是否能在最少指导下第一次就完成任务？

技术要求：文件结构

your-skill-name/
├── SKILL.md                  # 必需——主 Skill 文件
├── scripts/                  # 可选——可执行代码
│   ├── process_data.py       # 示例
│   └── validate.sh           # 示例
├── references/               # 可选——文档
│   ├── api-guide.md          # 示例
│   └── examples/             # 示例
└── assets/                   # 可选——模板等
    └── report-template.md    # 示例

关键规则

SKILL.md 命名

  • 必须准确命名为 SKILL.md（区分大小写）
  • 不接受任何变体（SKILL.MD、skill.md 等）

Skill 文件夹命名

  • 使用 kebab-case：notion-project-setup（正确）
  • 不能有空格：Notion Project Setup（错误）
  • 不能有下划线：notion_project_setup（错误）
  • 不能有大写字母：NotionProjectSetup（错误）
不要放置 README.md
  • Skill 文件夹内不要包含 README.md。
  • 所有文档都应放在 SKILL.md 或 references/ 中。
  • 注意：通过 GitHub 分发时，你仍需要一个面向人类用户的仓库级 README——参见“分发与分享”。

YAML frontmatter：最重要的部分

Claude 正是通过 YAML frontmatter 判断是否加载你的 Skill。务必把它写对。

最低必需格式：

---
name: your-skill-name
description: What it does. Use when user asks to [specific phrases].
---

起步只需要这些。

字段要求

name（必需）：

  • 只能使用 kebab-case
  • 不能有空格或大写字母
  • 应与文件夹名称一致

description（必需）：

  • 必须同时包含：这个 Skill 做什么；何时使用它（触发条件）
  • 少于 1024 个字符
  • 不能包含 XML 标签（< 或 >）
  • 包含用户可能会说出的具体任务
  • 如相关，提及文件类型

license（可选）：

  • Skill 开源时使用；常见值为 MIT、Apache-2.0。

compatibility（可选）：

  • 长度为 1–500 个字符
  • 说明环境要求，例如预期使用的产品、所需系统软件包、网络访问需求等

metadata（可选）：

  • 任意自定义键值对
  • 建议使用：author、version、mcp-server
metadata:
  author: ProjectHub
  version: 1.0.0
  mcp-server: projecthub

安全限制

frontmatter 中禁止：

  • XML 尖括号（<、>）
  • 名称中含有 claude 或 anthropic 的 Skill（保留名称）

原因：frontmatter 会出现在 Claude 的系统提示词中。恶意内容可能注入指令。

编写有效的 Skill：description 字段

Anthropic 工程博客指出：“这些元数据……提供刚好足够的信息，让 Claude 知道每个 Skill 应在何时使用，而不必将它的全部内容加载进上下文。”这就是渐进式披露的第一级。

结构：

[What it does] + [When to use it] + [Key capabilities]

优秀 description 示例：

# 好——具体且可执行
description: Analyzes Figma design files and generates developer handoff documentation. Use when user uploads .fig files, asks for "design specs", "component documentation", or "design-to-code handoff".

# 好——包含触发短语
description: Manages Linear project workflows including sprint planning, task creation, and status tracking. Use when user mentions "sprint", "Linear tasks", "project planning", or asks to "create tickets".

# 好——价值主张清晰
description: End-to-end customer onboarding workflow for PayFlow. Handles account creation, payment setup, and subscription management. Use when user says "onboard new customer", "set up subscription", or "create PayFlow account".

糟糕 description 示例：

# 太模糊
description: Helps with projects.

# 缺少触发条件
description: Creates sophisticated multi-page documentation systems.

# 过于技术化，没有用户触发语句
description: Implements the Project entity model with hierarchical relationships.

编写主要指令

在 frontmatter 之后，用 Markdown 编写实际指令。以下是推荐结构；请根据你的 Skill 调整模板，将方括号中的内容替换成具体内容。

---
name: your-skill
description: [...]
---

Chapter 3 · Testing and iteration测试与迭代

Skill 可以按不同严谨程度进行测试，具体取决于你的需求：

  • 在 Claude.ai 中手动测试：直接运行查询并观察行为。迭代快，无需设置。
  • 在 Claude Code 中脚本化测试：将测试用例自动化，以便跨变更进行可重复验证。
  • 通过 Skills API 进行程序化测试：构建评估套件，针对已定义的测试集系统运行。

应根据质量要求和 Skill 的可见范围选择合适方法。供小型团队内部使用的 Skill 与部署给数千名企业用户的 Skill，测试需求并不相同。

专业提示：先迭代单一任务，再扩大范围

我们发现，最有效的 Skill 创建者会先针对一个具有挑战性的任务反复迭代，直到 Claude 成功，再把成功的方法提取成 Skill。这样能利用 Claude 的上下文学习能力，并且比大范围测试更快获得有效信号。打好可用基础后，再扩展到多个测试用例以提高覆盖率。

推荐测试方法

根据早期经验，有效的 Skill 测试通常覆盖三个方面：

1. 触发测试

目标：确保 Skill 在正确的时机加载。

测试用例：

  • 应该在明显任务上触发
  • 应该在改写后的请求上触发
  • 不应在无关主题上触发

测试套件示例：

Should trigger:
- "Help me set up a new ProjectHub workspace"
- "I need to create a project in ProjectHub"
- "Initialize a ProjectHub project for Q4 planning"

Should NOT trigger:
- "What's the weather in San Francisco?"
- "Help me write Python code"
- "Create a spreadsheet" (unless ProjectHub skill handles sheets)

2. 功能测试

目标：验证 Skill 生成正确输出。

测试用例：

  • 生成有效输出
  • API 调用成功
  • 错误处理有效
  • 覆盖边界情况

示例：

Test: Create project with 5 tasks
Given: Project name "Q4 Planning", 5 task descriptions
When: Skill executes workflow
Then:
  - Project created in ProjectHub
  - 5 tasks created with correct properties
  - All tasks linked to project
  - No API errors

3. 性能对比

目标：证明 Skill 相比基线改善了结果。

使用“定义成功标准”中的指标。对比可能如下：

没有 Skill

  • 用户每次都提供指令
  • 15 次来回消息
  • 3 次 API 调用失败，需要重试
  • 消耗 12,000 tokens

有 Skill

  • 自动执行工作流
  • 只需 2 个澄清问题
  • 0 次 API 调用失败
  • 消耗 6,000 tokens

使用 skill-creator Skill

skill-creator Skill 可通过 Claude.ai 插件目录获取，也可下载用于 Claude Code；它能帮助你构建和迭代 Skill。如果你有 MCP 服务器，并知道最重要的 2–3 个工作流，就能在一次集中工作中构建并测试一个可用的 Skill——通常只需 15–30 分钟。

创建 Skill：

  • 根据自然语言描述生成 Skill
  • 生成带 frontmatter、格式正确的 SKILL.md
  • 建议触发短语和结构

审查 Skill：

  • 标记常见问题（模糊的 description、缺少触发条件、结构问题）
  • 识别潜在的触发不足或过度触发风险
  • 根据 Skill 声明的用途建议测试用例

迭代改进：

  • 使用 Skill 后遇到边界情况或失败时，把这些案例带回 skill-creator。
  • 示例：“使用本次对话中发现的问题与解决方案，改进 Skill 对 [specific edge case] 的处理方式。”

使用方式：

"Use the skill-creator skill to help me build a skill for [your use case]"
注意：skill-creator 可以帮助你设计和改进 Skill，但不会执行自动化测试套件，也不会生成定量评估结果。

根据反馈迭代

Skill 是持续演化的文档。应计划根据以下信号迭代：

触发不足信号

  • Skill 在本应加载时没有加载
  • 用户手动启用它
  • 支持问题集中在“什么时候使用”

解决方案：为 description 增加更多细节和细微差别——这可能包括关键词，尤其是技术术语。

过度触发信号

  • Skill 在无关查询上加载
  • 用户禁用它
  • 用户对用途感到困惑

解决方案：加入负向触发条件，表述得更具体。

执行问题

  • 结果不一致
  • API 调用失败
  • 需要用户纠正

解决方案：改进指令并添加错误处理。

Chapter 4 · Distribution and sharing分发与分享

Skill 会让你的 MCP 集成更加完整。当用户比较连接器时，带有 Skill 的连接器能让用户更快获得价值，从而相较仅有 MCP 的替代方案形成优势。

当前分发模式（2026 年 1 月）

个人用户如何获取 Skill：

  1. 下载 Skill 文件夹
  2. 压缩该文件夹（如需要）
  3. 通过 Claude.ai 的 Settings > Capabilities > Skills 上传
  4. 或者放进 Claude Code 的 Skills 目录

组织级 Skill：

  • 管理员可在整个工作区部署 Skill（已于 2025 年 12 月 18 日发布）
  • 自动更新
  • 集中管理

开放标准

我们已将 Agent Skills 发布为开放标准。与 MCP 一样，我们认为 Skill 应能跨工具和平台移植——无论你使用 Claude 还是其他 AI 平台，同一个 Skill 都应能够工作。尽管如此，有些 Skill 的设计会充分利用某一特定平台的能力；作者可以在 Skill 的 compatibility 字段中注明这一点。我们一直在与生态系统成员共同推进该标准，并对早期采用情况感到振奋。

通过 API 使用 Skill

对于以编程方式使用的场景——例如构建利用 Skill 的应用程序、智能体或自动化工作流——API 可让你直接控制 Skill 的管理和执行。

关键能力：

  • 用于列出和管理 Skill 的 /v1/skills 端点
  • 通过 container.skills 参数将 Skill 添加到 Messages API 请求
  • 通过 Claude Console 进行版本控制和管理
  • 可与 Claude Agent SDK 配合构建自定义智能体

何时通过 API 使用 Skill，何时使用 Claude.ai：

用例最佳界面

注意：API 中的 Skill 需要 Code Execution Tool beta，它提供运行 Skill 所需的安全环境。

当前推荐做法

先在 GitHub 上托管你的 Skill：使用公开仓库，提供清晰的 README（面向人类访客——它与 Skill 文件夹分开，Skill 文件夹本身不应包含 README.md），并提供带截图的使用示例。然后在 MCP 文档中增加一个链接到 Skill 的小节，解释两者结合使用的价值，并提供快速入门指南。

  1. 托管到 GitHub
    • 开源 Skill 使用公开仓库
    • 提供含安装说明的清晰 README
    • 提供用法示例和截图
  2. 在 MCP 仓库中编写文档
    • 从 MCP 文档链接到 Skill
    • 解释二者结合的价值
    • 提供快速入门指南
  3. 创建安装指南
## Installing the [Your Service] skill

1. Download the skill:
   - Clone repo: `git clone https://github.com/yourcompany/skills`
   - Or download ZIP from Releases

2. Install in Claude:
   - Open Claude.ai > Settings > skills
   - Click "Upload skill"
   - Select the skill folder (zipped)

3. Enable the skill:
   - Toggle on the [Your Service] skill
   - Ensure your MCP server is connected

4. Test:
   - Ask Claude: "Set up a new project in [Your Service]"

定位你的 Skill

你如何描述 Skill，会决定用户能否理解它的价值以及是否真的愿意尝试。在 README、文档或营销材料中介绍 Skill 时，请遵循以下原则。

聚焦结果，而不是功能：

好

“ProjectHub Skill 让团队能在几秒内建立完整的项目工作区——包括页面、数据库和模板——而不必花 30 分钟手动设置。”

差

“ProjectHub Skill 是一个包含 YAML frontmatter 和 Markdown 指令的文件夹，它会调用我们的 MCP 服务器工具。”

突出 MCP + Skills 的组合叙事：

“我们的 MCP 服务器让 Claude 能够访问你的 Linear 项目。我们的 Skill 教 Claude 使用你团队的 Sprint 规划工作流。两者结合，就能实现 AI 驱动的项目管理。”

Chapter 5 · Patterns and troubleshooting模式与故障排查

以下模式来自早期采用者和内部团队创建的 Skill。它们代表我们观察到效果良好的常见做法，而不是必须遵循的模板。

选择方法：问题优先还是工具优先

可以把它想成逛 Home Depot。你可能带着一个问题进去——“我需要修好一个厨房橱柜”——然后员工会为你指出正确的工具。你也可能先挑中一把新电钻，再问如何把它用于自己的具体工作。

Skill 的工作方式也一样：

  • 问题优先：“我需要建立一个项目工作区” → 你的 Skill 按正确顺序编排正确的 MCP 调用。用户描述结果，Skill 负责工具。
  • 工具优先：“我已经连接了 Notion MCP” → 你的 Skill 教 Claude 最优工作流与最佳实践。用户拥有访问能力，Skill 提供专业知识。

大多数 Skill 都会偏向其中一种。了解哪种框架适合你的用例，有助于从下面选择正确模式。

模式 1：顺序工作流编排

适用场景：用户需要以特定顺序执行多步骤流程。

结构示例：

## Workflow: Onboard New Customer

### Step 1: Create Account
Call MCP tool: `create_customer`
Parameters: name, email, company

### Step 2: Setup Payment
Call MCP tool: `setup_payment_method`
Wait for: payment method verification

### Step 3: Create Subscription
Call MCP tool: `create_subscription`
Parameters: plan_id, customer_id (from Step 1)

### Step 4: Send Welcome Email
Call MCP tool: `send_email`
Template: welcome_email_template

关键技术：

  • 明确步骤顺序
  • 步骤之间的依赖关系
  • 每个阶段都进行验证
  • 失败时的回滚指令

模式 2：多 MCP 协调

适用场景：工作流跨越多个服务。

示例：从设计到开发的交接

### Phase 1: Design Export (Figma MCP)
1. Export design assets from Figma
2. Generate design specifications
3. Create asset manifest

### Phase 2: Asset Storage (Drive MCP)
1. Create project folder in Drive
2. Upload all assets
3. Generate shareable links

### Phase 3: Task Creation (Linear MCP)
1. Create development tasks
2. Attach asset links to tasks
3. Assign to engineering team

### Phase 4: Notification (Slack MCP)
1. Post handoff summary to #engineering
2. Include asset links and task references

关键技术：

  • 清晰划分阶段
  • 在不同 MCP 之间传递数据
  • 进入下一阶段前进行验证
  • 集中化错误处理

模式 3：迭代优化

适用场景：输出质量会随着迭代而提高。

示例：生成报告

## Iterative Report Creation

### Initial Draft
1. Fetch data via MCP
2. Generate first draft report
3. Save to temporary file

### Quality Check
1. Run validation script: `scripts/check_report.py`
2. Identify issues:
   - Missing sections
   - Inconsistent formatting
   - Data validation errors

### Refinement Loop
1. Address each identified issue
2. Regenerate affected sections
3. Re-validate
4. Repeat until quality threshold met

### Finalization
1. Apply final formatting
2. Generate summary
3. Save final version

关键技术：

  • 明确的质量标准
  • 迭代改进
  • 验证脚本
  • 知道何时停止迭代

模式 4：上下文感知的工具选择

适用场景：结果相同，但根据上下文使用不同工具。

示例：文件存储

## Smart File Storage

### Decision Tree
1. Check file type and size
2. Determine best storage location:
   - Large files (>10MB): Use cloud storage MCP
   - Collaborative docs: Use Notion/Docs MCP
   - Code files: Use GitHub MCP
   - Temporary files: Use local storage

### Execute Storage
Based on decision:
- Call appropriate MCP tool
- Apply service-specific metadata
- Generate access link

### Provide Context to User
Explain why that storage was chosen

关键技术：

  • 明确的决策标准
  • 后备选项
  • 对所做选择保持透明

模式 5：领域专用智能

适用场景：Skill 提供超越工具访问的专业知识。

示例：金融合规

## Payment Processing with Compliance

### Before Processing (Compliance Check)
1. Fetch transaction details via MCP
2. Apply compliance rules:
   - Check sanctions lists
   - Verify jurisdiction allowances
   - Assess risk level
3. Document compliance decision

### Processing
IF compliance passed:
  - Call payment processing MCP tool
  - Apply appropriate fraud checks
  - Process transaction
ELSE:
  - Flag for review
  - Create compliance case

### Audit Trail
- Log all compliance checks
- Record processing decisions
- Generate audit report

关键技术：

  • 将领域专长嵌入逻辑
  • 先合规，再行动
  • 完整记录
  • 清晰治理

故障排查：Skill 无法上传

错误：Could not find SKILL.md in uploaded folder

原因：文件没有准确命名为 SKILL.md。

解决方案：

  • 重命名为 SKILL.md（区分大小写）
  • 使用 ls -la 验证，输出应显示 SKILL.md

错误：Invalid frontmatter

原因：YAML 格式问题。

常见错误：

# 错误——缺少分隔符
name: my-skill
description: Does things

# 错误——引号未闭合
name: my-skill
description: "Does things

# 正确
---
name: my-skill
description: Does things
---

错误：Invalid skill name

原因：名称中包含空格或大写字母。

# 错误
name: My Cool Skill

# 正确
name: my-cool-skill

故障排查：Skill 不触发

症状：Skill 从不自动加载。

修复：修改 description 字段。优秀与糟糕示例请参阅“description 字段”。

快速检查清单：

  • 它是否太笼统？（“帮助处理项目”不会奏效）
  • 是否包含用户实际会说出的触发短语？
  • 如果适用，是否提到相关文件类型？

调试方法：询问 Claude：“你会在什么时候使用 [skill name] Skill？”Claude 会引用 description。根据缺失内容进行调整。

故障排查：Skill 触发过于频繁

症状：Skill 在无关查询上加载。

解决方案 1：添加负向触发条件

description: Advanced data analysis for CSV files. Use for statistical modeling, regression, clustering. Do NOT use for simple data exploration (use data-viz skill instead).

解决方案 2：表述得更具体

# 太宽泛
description: Processes documents

# 更具体
description: Processes PDF legal documents for contract review

解决方案 3：明确范围

description: PayFlow payment processing for e-commerce. Use specifically for online payment workflows, not for general financial queries.

故障排查：MCP 连接问题

症状：Skill 已加载，但 MCP 调用失败。

检查清单：

  1. 确认 MCP 服务器已连接
    • Claude.ai：Settings > Extensions > [Your Service]
    • 应显示 Connected 状态
  2. 检查身份验证
    • API 密钥有效且未过期
    • 已授予正确权限或 scope
    • OAuth token 已刷新
  3. 独立测试 MCP
    • 让 Claude 直接调用 MCP（不使用 Skill）
    • “Use [Service] MCP to fetch my projects”
    • 如果这里失败，问题在 MCP，而不是 Skill
  4. 确认工具名称
    • Skill 引用了正确的 MCP 工具名
    • 检查 MCP 服务器文档
    • 工具名称区分大小写

故障排查：指令未被遵循

症状：Skill 已加载，但 Claude 没有遵循指令。

常见原因：

  1. 指令过于冗长
    • 保持指令简洁
    • 使用项目符号和编号列表
    • 将详细参考资料移到单独文件
  2. 指令埋得太深
    • 把关键指令放在顶部
    • 使用 ## Important 或 ## Critical 标题
    • 必要时重复关键点
  3. 语言含糊

差

Make sure to validate things properly

好

CRITICAL: Before calling create_project, verify:
- Project name is non-empty
- At least one team member assigned
- Start date is not in the past

高级技巧：对于关键验证，可考虑捆绑一个以编程方式执行检查的脚本，而不是依赖自然语言指令。代码是确定性的，语言解释则不是。有关这种模式的示例，请参阅 Office Skills。

4. 模型“偷懒”——添加明确鼓励：

## Performance Notes
- Take your time to do this thoroughly
- Quality is more important than speed
- Do not skip validation steps
注意：把这些内容加入用户提示词，比放在 SKILL.md 中更有效。

故障排查：大上下文问题

症状：Skill 看起来很慢，或者回答质量下降。

原因：

  • Skill 内容过大
  • 同时启用的 Skill 太多
  • 所有内容都被加载，没有使用渐进式披露

解决方案：

  1. 优化 SKILL.md 大小
    • 将详细文档移到 references/
    • 链接参考资料，而不是内联全部内容
    • 保持 SKILL.md 少于 5,000 词
  2. 减少启用的 Skill
    • 如果同时启用了 20–50 个以上 Skill，评估是否确有必要
    • 建议选择性启用
    • 考虑将相关能力组织成 Skill “包”

参考 A：快速检查清单

使用本清单在上传前后验证 Skill。如果希望更快开始，可以先用 skill-creator Skill 生成初稿，再逐项检查，确保没有遗漏。

开始之前

  • 已确定 2–3 个具体用例
  • 已确定所需工具（内置工具或 MCP）
  • 已阅读本指南和示例 Skill
  • 已规划文件夹结构

开发期间

  • 文件夹使用 kebab-case 命名
  • SKILL.md 文件存在（拼写完全准确）
  • YAML frontmatter 使用 --- 分隔符
  • name 字段使用 kebab-case，无空格、无大写字母
  • description 同时包含“做什么”和“何时使用”
  • 任何位置都没有 XML 标签（<、>）
  • 指令清晰且可执行
  • 包含错误处理
  • 提供了示例
  • 清晰链接了参考资料

上传之前

  • 已测试在明显任务上的触发
  • 已测试在改写请求上的触发
  • 已验证不会在无关主题上触发
  • 功能测试通过
  • 工具集成有效（如适用）
  • 已压缩为 .zip 文件

上传之后

  • 在真实对话中测试
  • 监控触发不足或过度触发
  • 收集用户反馈
  • 迭代 description 和指令
  • 更新 metadata 中的版本

参考 B：YAML frontmatter

必需字段：

---
name: skill-name-in-kebab-case
description: What it does and when to use it. Include specific trigger phrases.
---

所有可选字段：

name: skill-name
description: [required description]
license: MIT # 可选：开源许可证
allowed-tools: "Bash(python:*) Bash(npm:*) WebFetch" # 可选：限制工具访问
metadata: # 可选：自定义字段
  author: Company Name
  version: 1.0.0
  mcp-server: server-name
  category: productivity
  tags: [project-management, automation]
  documentation: https://example.com/docs
  support: support@example.com

安全说明

允许

  • 任何标准 YAML 类型（字符串、数字、布尔值、列表、对象）
  • 自定义 metadata 字段
  • 最长 1024 个字符的长 description

禁止

  • XML 尖括号（<、>）——安全限制
  • 在 YAML 中执行代码（系统使用安全 YAML 解析）
  • 以 claude 或 anthropic 为名称前缀的 Skill（保留）
