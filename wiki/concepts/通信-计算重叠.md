# 通信-计算重叠

## 定义

通信-计算重叠是把数据传输、同步等待与不依赖该数据的计算安排在同一时间窗口执行，以缩短端到端关键路径。它不减少逻辑通信量，而是利用网络、Copy Engine、SM、Tensor Core 等资源和细粒度依赖的差异隐藏部分通信时间。

## 成立条件

重叠的关键不是“全部数据传完才能开始计算”，而是识别更细粒度的依赖：

- 不同 microbatch 彼此独立，可以让一批通信覆盖另一批计算。
- MoE token 会陆续到达，某个 expert/tile 的输入到齐后可以先计算，不必等待所有 expert。
- 一次通信可以拆成“发起”和“完成”，中间执行不依赖接收结果的工作。
- 不同 warp/CTA/SM 可以承担通信、搬运、计算或 relay 角色。

如果下一步计算严格依赖完整通信结果，或者通信与计算争用同一瓶颈资源，理论并发不一定带来实际隐藏。

## NCCL EP 的 staged execution

`nccl_ep` 的 Low-Latency 路径支持 `send_only`：先发起 dispatch 发送，把后续接收状态保存在 handle 中，再由 `ncclEpComplete` 完成接收阶段。

```text
Dispatch send
-> 执行其他可并行工作
-> ncclEpComplete / receive
-> 消费到达的 token
```

这创造了调度窗口，但不自动保证提速；上层仍需找到可执行的独立计算，并避免错误地消费尚未到达的数据。

High-Throughput 路径则按拓扑组织域内 LSA/NVLink 搬运和跨域 GIN/RDMA，并使用不同 warp group 和 pipeline stage 处理跨域传输、gather/scatter 与布局整理。

## 设备侧同步

把更多热路径推进 Device 侧，可以减少每个小阶段都返回 Host 的调度开销。来源中的 LL kernel 在 GPU 上处理：

- 等待远端 token 和计数；
- signal 与到达状态；
- rank mask、timeout 和 async error；
- Window-backed tensor 和 one-sided 数据移动。

这不意味着 CPU 被完全移除。Host 仍负责 communicator、配置、拓扑分析、JIT 选择和传输计划。更准确的系统分层是：

```text
Host：规划、校验、选择策略
Device：执行高频通信与同步热路径
```

## Ring Attention 的 KV 流水

[[Ring Attention]] 保持本地 Query chunk 不动，让 K/V blocks 沿 ring 逐轮传递。每轮在计算当前 block Attention 的同时发送下一块 K/V，并用 [[Online Softmax]] 累积精确结果。序列足够长时，block compute 可覆盖 P2P；序列短或 CP degree 太高时，多轮启动延迟和 tail 会暴露。

相比之下，[[DeepSpeed Ulysses]] 在 Attention 前后使用 All-to-All 完成 layout transpose，collective 阶段边界更明确，通常不如 Ring 容易做逐 block 重叠。

## DBO 与 MegaMoE：两种重叠粒度

[[Dual Batch Overlap]] 在 runtime 层交错两个 microbatch：一个等待 MoE dispatch/combine 时，另一个推进 GPU 工作。[[MegaMoE]] 则在单 batch 内按 expert wave 交错 dispatch、L1、activation、L2 与 combine。

前者是跨 microbatch 调度，不要求融合 kernels；后者是算子/流水内部的细粒度融合。二者概念上可组合，但若后者已同时占满 Tensor Core、HBM 和互联，再加 DBO 可能只增加争用和功耗。

## PD 状态传输与下一轮 Prefill 重叠

vLLM x TileRT 来源在 Prefill forward window 内、cache blocks 回收前把请求状态复制到 staging buffer，再由后台 sender 通过 Mooncake/NIXL 执行 RDMA one-sided writes。这样网络传输可与共享 Prefill pool 的下一轮执行重叠，包括同 batch 中走 native Decode 的请求。

这并非零开销：state extraction、本地 copy、staging capacity 和网络仍占资源；当发送速度跟不上 Prefill 产出时，会在 buffer、网络或 Decode admission 处形成背压。

## Counted fabric operation

[[../entities/NVIDIA Rubin]] 来源描述的 counted put/reduction 让 GPU kernel 发起跨 GPU 数据移动，并按目标端实际访问字节数更新 remote counter。接收端轮询 counter 达到预期值后即可消费数据，减少独立 memory barrier、acknowledgment 和 atomic flag 的协调，适合 MoE dispatch/combine 等高频细粒度数据流。

需要注意：来源指出相关 counted fabric syntax 在 PTX 9.3、最低 target `sm_100+` 已出现。Rubin 的产品能力、Blackwell 的指令 target 与具体 CUDA/NVLink 软件可用性不能混为一谈，仍需实机和支持矩阵核实。

## 重叠粒度

- **跨 microbatch**：实现简单，但需要足够并发，并可能增加排队或版本管理复杂度。
- **阶段级**：把 send/receive 或 dispatch/complete 拆开，在中间插入独立计算。
- **Token/tile 级**：某个 expert tile 数据到齐即计算，潜在重叠更细，但需要 scoreboard/signal 和更复杂调度。
- **Warp/SM 级**：不同执行单元专职通信、relay 和 GEMM，控制最细，工程与正确性成本也最高。

## 关键权衡

- 重叠优化关注关键路径，不等同于减少总通信字节。
- 需要双缓冲、状态句柄、signal 或 scoreboard，可能增加显存、寄存器和同步开销。
- 通信与计算若同时争用 SM、HBM 或 L2，会互相降速；“同时执行”不等于“完全隐藏”。
- 负载不均、晚到 token 和热门 expert 会形成尾部等待。
- 分阶段 API、超时、mask 和异步错误处理会提高状态机复杂度。
