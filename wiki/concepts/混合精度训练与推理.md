# 混合精度训练与推理

## 定义

在同一个训练或推理 workload 中混合使用多种数值精度，例如让大部分 matmul/attention 路径使用 `FP16 / BF16 / FP8`，同时把更脆弱的累加、统计量或参数更新保留在更高精度。

## 它解决什么问题

- 降低参数、激活和缓存的显存占用
- 降低 memory traffic，提高吞吐
- 更好地利用 `Tensor Core` 等低精度高吞吐硬件路径

## 核心机制

- 把“高吞吐但可容忍低精度”的路径与“数值敏感”的路径拆开
- 常见做法是低精度输入、较高精度累加，并把部分更新状态保留在 `FP32`
- 训练与推理都不只是切换 dtype，还要同时考虑通信、缓存、布局和 kernel 支持

## 训练关键点

- `FP16` 训练常见风险是梯度下溢，因此经常需要 `loss scaling`
- `BF16` 动态范围更接近 `FP32`，通常更稳，但并不意味着所有 reduction 都能安全降精度
- 优化器更新路径里常保留 `FP32 master weights`
- 梯度裁剪、`all-reduce`、norm 统计量和 `softmax` 这类步骤通常要额外关注累加精度

## 推理关键点

- 权重精度、激活精度和累加精度要分开看，不能把“混合精度”和“量化”完全混为一谈
- `Prefill` 更容易吃到低精度大矩阵计算的收益，`Decode` 往往更偏 [[KV Cache]] 读写和带宽瓶颈
- `KV Cache` 本身也是精度优化对象，但降精度会影响长上下文质量与误差累积
- 频繁 `cast / dequant` 也会带来额外 kernel 和带宽开销，因此低精度不一定自动更快
- [[../entities/RTP-LLM]] 来源把 FP8/INT8/INT4 KV cache 量化作为推理优化重点之一，强调它主要缓解 Decode 阶段的显存容量和带宽压力

## RL 训推一致性中的精度边界

在线 RL 常让 Trainer 的 teacher-forcing full forward 与 Rollout engine 的 prefill/decode 使用不同 dtype、Attention backend、KV Cache 精度和 reduction 路径。即使权重与 token 完全相同，BF16/FP16/FP8、量化 cache、PagedAttention 和 TP 规约顺序也可能带来非 bitwise 的 per-token logprob 差异。

[[RL 训推不一致]] 的诊断不应一开始就把所有低精度路径视为错误：应先在高精度/eager/简化并行配置下建立条件 logprob 基线，再逐项恢复真实 kernel 与量化。小幅无方向噪声可能可接受；大面积同方向、随位置累积或使 importance ratio 明显偏离 `1` 的差异需要继续定位。可接受阈值必须绑定模型、序列长度、dtype、后端与 RL loss，不能套用来源文章中的单一经验范围。

## FP4 / MXFP4 / NVFP4

- `FP4` 单个元素常见核心编码是 `E2M1`，即 1 个 sign bit、2 个 exponent bits、1 个 mantissa bit；单独的 4-bit 值动态范围很有限，所以真实训练/推理格式通常还要配合 block scale。
- `MXFP4` 是 OCP Microscaling Formats 里的开放 microscaling 格式：每 32 个 `FP4 E2M1` 元素共享 1 个 `E8M0` scale。`E8M0` 只有 exponent、没有 mantissa，本质上更接近 power-of-two scale，硬件实现简单，但 scale 精度较粗。
- `NVFP4` 是 NVIDIA 面向 Blackwell / Transformer Engine 的 FP4 recipe：每 16 个 `FP4 E2M1` 元素共享 1 个 `FP8 E4M3` block scale，并叠加 1 个 per-tensor `FP32` global scale。相比 MXFP4，它的 block 更小、scale 有 mantissa，通常是为了换更低量化误差。
- 对 GEMM 来说，这类格式不是把矩阵“直接当 4-bit 数相乘”这么简单，而是近似执行 `(A_fp4 * scale_a) @ (B_fp4 * scale_b)`；scale 的布局、广播方向和硬件 kernel 支持会直接影响性能。

## Rubin 低精度峰值与 LUT 解压

[[../entities/NVIDIA Rubin]] 来源转述的整卡峰值包括 dense NVFP4 35 PFLOPS、dense FP8 17.5 PFLOPS，并指出部分低精度 Tensor Core 路径提高 K 维吞吐。峰值变化同时受 SM 数、单 Tensor Core 吞吐和可能的频率变化影响，不能直接作为真实 kernel 加速比。

PTX 9.4 中的 `tcgen05.mma.decompress::lut::b` 被来源解释为局部 codebook 解压：B operand 保存 3-bit index，每个 local group 有 8 个 E4M3 候选，MMA 内部选择并恢复 B value。它不是任意函数的通用 LUT；实际收益还依赖编码、collector 复用、布局与量化误差。

## LatentMoE 来源中的低精度路线

二手来源将 Nemotron 3 Super 与 NVFP4、Kimi K3 与 MXFP4 权重/MXFP8 激活关联起来，意图说明潜在空间压缩可与低精度共同降低 expert 权重和部署成本。由于当前缺少对应官方报告，这些模型规格和训练 recipe 仅作为待核实线索，不能写成通用 LatentMoE 必须使用的精度方案。

## 关键权衡

- 低精度通常能显著提升吞吐并降低显存，但数值稳定性、收敛速度和长上下文质量会更敏感
- 真正可用的方案通常不是“全程低精度”，而是“高吞吐路径低精度，数值脆弱路径高精度”
- 是否值得继续降到 `FP8` 或更低，强依赖硬件支持、缩放策略和 workload 容错性，部分细节仍需结合具体框架与硬件验证

## 研究备注

- 现有 wiki 里与“低精度提升吞吐”相关的硬件直觉主要来自 [[../sources/斯坦福CS336 Lecture 5 - GPUs]]；`loss scaling`、`FP32 master weights` 和更细的训练配方主要依赖 NVIDIA 官方文档
- 后续可继续补 `FP16 vs BF16 vs FP8` 在训练与推理中的更细粒度 recipe，以及和量化路径的边界
- 面试诊断低精度推理是否真正生效时，应同时看 dtype 配置和硬件管线指标：如果 BF16/FP16 模型的热点 GEMM 没有带来 `Tensor Active`，反而 `FP32 pipe active` 异常高，通常要检查 shape、layout、backend fallback 和 cast/dequant 开销。
- RTP-LLM 来源中的 `FP8 KV cache` 延迟和 PPL 结果应保留为来源声称；长上下文质量、不同模型族和不同硬件上的误差边界仍需单独复测。
- `NVFP4` 与 `MXFP4` 都应理解为 block-scaled FP4 格式，而不是裸 `E2M1`；比较二者时优先看 block size、scale dtype、global scale、硬件支持和 quantization recipe。
