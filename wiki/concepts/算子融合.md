# 算子融合

## 定义

把多个原本分开的算子合并进更少的 kernel 执行，以减少中间结果写回与再次读取的优化方法。

## 它解决什么问题

- 降低中间张量频繁进出 global memory 的成本
- 提升低 arithmetic intensity 操作链的整体效率

## 核心机制

- 将多个 pointwise 或局部可组合的操作融合为更少的 kernel
- 避免中间结果反复落回慢速内存
- 让一次数据读取服务更多计算步骤
- 真正的设计起点通常是数据流而不是算子名字：先找最大的中间张量和重复读写点，再决定哪些阶段应留在寄存器或 shared memory
- 融合边界往往由数据局部性、同步需求和寄存器/shared memory 压力共同决定，而不是简单按“语义相邻”划线
- [[CODA]] 是一个更结构化的融合例子：它不是简单拼接相邻 PyTorch op，而是把 Transformer 中部分 memory-bound 小操作通过代数重写表达为 `GEMM + epilogue` 程序，让中间状态尽量在 GEMM 写回 HBM 前完成处理。
- [[Megakernel]] 是更激进的融合方向：它不只融合相邻 op，而是尝试把整次 Llama-1B forward pass 放进单个 kernel，以消除 kernel launch、尾部波次和权重加载断流造成的 pipeline bubbles。

## 关键权衡

- 融合通常能显著减少访存，但会提高 kernel 实现复杂度
- 过度融合可能增加寄存器压力、编译复杂度或降低调试可读性
- 某些融合虽然减少了 launch 次数，却可能因为 occupancy 下降或共享同一个次优 launch 形态而变慢
- 不是所有相邻算子都适合合成一个“超大算子”：如果不同阶段需要不同 tile shape、线程映射、同步方式或 Tensor Core 路径，强行融合可能让每一段都运行在折中的次优配置上。
- 当融合后单线程寄存器使用过高，可能降低 [[Occupancy]]，甚至触发 register spilling 到 local memory；这会把原本省下的 HBM traffic 又以另一种形式还回来。
- 融合边界应优先围绕数据复用和中间张量大小决定：大中间张量、pointwise epilogue、norm + activation、bias + residual 这类常见路径更适合融合；跨越复杂 GEMM、collective communication、动态 shape 或强同步边界时要更谨慎。

## 面试回答模板

> 算子融合不是越多越好。它的核心收益是减少 kernel launch 和中间张量的 HBM 写回/读入，尤其适合 memory-bound 的 pointwise 链、epilogue、norm、activation、bias/residual 这类局部操作。但如果为了融合把很多计算形态不同的阶段塞进一个超大 kernel，可能会带来寄存器压力、shared memory 压力、occupancy 下降、register spilling、warp divergence、编译和调试复杂度上升，还可能让不同阶段只能共用一个次优 tile/线程布局。所以工程上应该先做数据流和 roofline 账本：哪些中间结果最大、哪些读写最浪费、哪些阶段局部性一致，再决定融合边界，而不是机械地把所有相邻算子都融合。

## 研究备注

- 后续可补 `torch.compile`、Triton 和手写 CUDA kernel 在融合路径上的分工差异
- 一个稳妥的实践顺序是：先做中间张量读写账本，再决定 fuse 不 fuse，而不是看到连续算子就机械拼接
- `mHC` 是一个很好的系统案例：论文把系数计算、残差合并、轻量 coefficient 操作和 `Sinkhorn-Knopp` 投影分别做成 fused kernels，并用 TileLang 承担大部分 kernel 实现
- CODA 适合补充为“代数重写驱动的 epilogue fusion”案例；其 benchmark 数字应待原论文和代码核实后再引用。
- Megakernel 说明“融合不是越大越好”的另一面：只有在 kernel 边界开销、tail effect 和 load bubble 已经主导端到端 latency 的窄场景里，整模型级融合才可能抵消其同步、调度和维护复杂度。
